# Ubiquitous Language

This is the shared vocabulary for Vaier. Use these terms exactly — in code, commit messages, issues, PRD entries, UI copy, and conversation. When two words could mean the same thing, only the term listed here is correct. Every term here is operator-facing by default; §17 lists the exceptions — the ones that are internal vocabulary and are never said to the operator, and what the UI says in their place.

Terms are drawn from the domain model (`src/main/java/net/vaier/domain/`), the use-case ports, REST APIs, the PRD, the README, and active GitHub issues. When the codebase and the docs disagree, the codebase wins and this document gets updated.

## 1. Product

| Term | Definition |
|------|------------|
| **Vaier** | The product. Also the name of the Spring Boot application container in the Docker Compose stack. |
| **Vaier server** | The single Linux host that runs the full Compose stack (WireGuard, Traefik, oauth2-proxy, Vaier). Has one public IP and is the WireGuard gateway. There is exactly one. Also appears in the **Explorer** as a singleton machine under its reserved name `"Vaier server"` (`LanAnchor.VAIER_SERVER_NAME`) — no operator peer or LAN server may reuse it — carrying the same **SSH access** toggle and **host credential** control as any other machine. It is infrastructure, so its pane offers no delete/regenerate/publish. Its SSH-access override is stored in the **Vaier config** (it is neither a peer nor a LAN server). |
| **Vaier app** | Vaier's own Android app: the client a phone runs to join and use the fleet, in place of the WireGuard app. Obtained from the **Vaier server** itself — the **launchpad** shows an **install card** offering the signed package the running image ships, with no app store and no account — and the card appears only on an Android phone, and only when that image actually carries a package. The copy handed out carries a **stamped host**, so the app knows which Vaier served it and never asks for an address. It is what a phone **enrols** from, so a peer created through it has a **device-held key**. Always "the Vaier app", never "the mobile app" or "the client". |
| **Stamped host** | The **Vaier server**'s own host name, written into the **Vaier app**'s package as it is served, so the app knows which Vaier it came from. It is carried in the package's APK Signing Block, which no signature covers, so the package stays signed exactly as it was built — Vaier holds no signing key. Replaced, never repeated, if the same package is served again. |
| **Install card** | The **launchpad**'s offer of the **Vaier app**: the app's mark, its name, one line, and an **Install** button. Shown only where it can be acted on — an Android phone, on a deployment carrying a package. Sits at the foot of the page, below the fleet, and is never dismissed. |
| **Operator** | The human running Vaier — typically a homelab developer. Not "user" (which means an access entry). |
| **Stack** | The long-running containers in `docker-compose.yml`: `wireguard`, `traefik`, `docker-proxy`, `oauth2-proxy`, `dex`, `vaier`, and `vaier-offline`, alongside sidecar/init helpers. `authelia` and `redis` were removed when social login replaced Authelia as the running auth gateway. Stack components are upstream and pinned by tag — never floating `:latest`. |
| **Configured administrator** | The email (`VAIER_ADMIN_EMAIL`) Vaier seeds as the first **admin** **access entry** when the access store is empty, and restores to admin on startup whenever no admin remains. The way the operator first reaches the admin-only console under social login. |
| **Concepts page** | The in-app, operator-facing glossary shown inside the admin shell: a trimmed, plain-language subset of this document's terms, grouped, each with a short definition and a one-line "why it matters". Its terms are a curated subset of the ones defined here. |
| **Infrastructure** | The operator's machine-and-service management surface. No longer a distinct page or admin-shell section: adding, monitoring and editing machines, the world **Map**, publishing and managing published services, the **LAN scanner**, **host credentials** and setup scripts all live in the **Explorer** now, and the former Infrastructure page is gone. The launchpad and admin nav no longer label it — they link to the **Explorer** by name — and it survives only as the old `#infrastructure` link/hash that still resolves to the Explorer. Earlier still it replaced the separate **Machines** and **Services** pages, which also no longer exist. |

## 2. Machines and peers

The unified term is **machine**. A machine is anything Vaier knows about that can host services or connect to the VPN.

| Term | Definition |
|------|------------|
| **Machine** | Read projection (`domain.Machine`) covering every host Vaier manages. Identified by its **machine id**; carries a `MachineType` and a **name**, which is a label and need not be unique. Returned by `GET /machines`. |
| **MachineType** | Enum with five values: `MOBILE_CLIENT`, `WINDOWS_CLIENT`, `UBUNTU_SERVER`, `WINDOWS_SERVER`, `LAN_SERVER`. The first four are **VPN peers**; the fifth is not. The **routing** concept — it drives WireGuard client/server config. Distinct from **device category**, which is icon-only. |
| **Device category** | The kind of device a machine is (`domain.DeviceCategory`: `PHONE`, `LAPTOP`, `DESKTOP`, `SERVER`, `NAS`, `PRINTER`, `ROUTER`, `GATEWAY`, `IOT`, `CAMERA`, `MEDIA`, `GENERIC`). A purely presentational, orthogonal attribute: it picks the icon shown for a machine and never affects routing, keys, or how a service is exposed. It also *seeds* a machine's **SSH access** default (a printer/phone starts off, a server/NAS starts on) — a presentational convenience only; the SSH-access flag is authoritative and, once set, the category never affects it. `GENERIC` is the fallback when nothing else signals. Distinct from **machine type**, which is the routing concept — a NAS and a desktop may both be `UBUNTU_SERVER` peers yet carry different device categories. Within the enum, `ROUTER` (a LAN router or Wi-Fi access point) and `GATEWAY` (an internet-edge or IoT-hub bridge, e.g. a Zigbee/Z-Wave or Home Assistant hub) are separate categories, not synonyms; the device-category `GATEWAY` is also unrelated to the routing-level **gateway peer**. |
| **Effective device category** | The **device category** actually shown for a machine: its **device category override** when one is set, otherwise the auto-detected category. Never blank — falls back to `GENERIC`. |
| **Device category override** | An explicit **device category** an operator pins on a machine, taking precedence over auto-detection. Optional; when absent the machine uses its detected category, and clearing it reverts to auto-detection. |
| **SSH access** | A per-machine flag for whether Vaier offers SSH — the host-credential control now, the web terminal later — for that machine. Authoritative and independent of routing. The persisted value is an explicit operator override; when unset, the **effective** value falls back to a smart default seeded from the machine's device type (a server/NAS/desktop/laptop starts on; an appliance such as a printer, phone, router, or camera starts off). Stored per machine where that machine lives — peer `# VAIER:` metadata, `lan-servers.yml`, or the **Vaier config** for the Vaier server itself. An operator's *intent* to allow SSH — distinct from **SSH server presence**, Vaier's observation of whether a server actually answers. |
| **VPN peer** / **peer** | A machine connected to Vaier over WireGuard. Equivalent to "MachineType where `isVpnPeer()` is true". Use "peer" in UI and casual reference; "VPN peer" when disambiguating from a LAN server. |
| **Client peer** | Mobile or Windows client; default `AllowedIPs = 0.0.0.0/0` (full tunnel). Cannot host containers in the Vaier model. |
| **Server peer** | `UBUNTU_SERVER` or `WINDOWS_SERVER`; default `AllowedIPs` is the VPN subnet only (split tunnel). Can host Docker containers. `MachineType.isServerType()` also returns true for `LAN_SERVER`. |
| **Machine intent** | The intent-first expression of what an operator is adding a peer *for* — `SERVER` or `PERSONAL_DEVICE` (`domain.MachineIntent`). Together with whether the machine runs Windows it resolves to one of the four peer **MachineType**s; that mapping is a domain decision. The operator states intent and OS in plain terms and Vaier picks the routing type. Distinct from **MachineType**, the routing concept the intent resolves to. |
| **LAN server** | A non-WireGuard machine that Vaier knows about — NAS, IPMI host, printer, extra Docker host — sitting either on a **relay peer's** LAN or in the **Vaier server's own LAN** (server LAN CIDR). Persisted in `lan-servers.yml`. Docker is optional; when on, Vaier scrapes its remote socket *through the relay*, or — for a server-anchored LAN server — directly from the Vaier-side containers. Registration requires the `lanAddress` to fall inside some relay peer's `lanCidr` or the server LAN CIDR; the UI asks only for the address. |
| **Relay peer** | A server peer with a `lanCidr` set. Vaier routes traffic for that CIDR into the relay's tunnel, and the relay's install script enables `ip_forward` and idempotent iptables NAT/FORWARD rules so packets reach LAN hosts behind it. The rules are re-applied on every boot by a generated `vaier-wg-relay-iptables.service` systemd oneshot. A machine in the Vaier server's *own* subnet does not need a relay peer — see **server LAN CIDR**. |
| **LAN anchor** | What routes packets to a LAN address: a relay peer whose `lanCidr` contains it, or — failing that — the Vaier server itself, when the address is inside the **server LAN CIDR**. When both match, the relay peer wins. Modelled by `domain.LanAnchor`; the Vaier-server anchor surfaces under the canonical name `"Vaier server"` (`LanAnchor.VAIER_SERVER_NAME`) wherever a relay peer name would otherwise appear. Resolved via `ResolveLanAnchorUseCase` and exposed at `GET /lan-servers/lan-anchor?address=…` (`{routable, routedVia, cidr}`), so the Add Machine modal asks the domain whether a typed address is routable instead of doing CIDR math in the browser. |
| **Scannable LAN** | A LAN Vaier can sweep for unregistered hosts: a **relay peer's** routed LAN, or the **Vaier server's own LAN**, each identified by its **LAN anchor** and shown to the operator as *via <name>* with its CIDR. The operator always picks one scannable LAN first; the **LAN scanner** then sweeps only that LAN. |
| **LAN setup script** | The single shell script an operator runs on a registered **LAN server** to prepare it for Vaier. It adapts to the host: it exposes the host's Docker engine API when the LAN server runs Docker, and installs persistent routes into the Vaier network (the **server LAN CIDR**, the **VPN subnet**, and other **relay peers'** LANs) via the host's relay peer when the host is relay-anchored. Idempotent. Supersedes the earlier Docker-only setup script. Offered only for a LAN server with a shell to run it in: an appliance category (IoT, printer, camera, router, media box) is taken to have none unless it runs Docker or the operator granted **SSH access**, however it is anchored, so the Explorer shows no **Setup command** for it and the setup-token route answers that there is nothing to set up (`Machine.acceptsSetupScript()`, `LanServer.acceptsSetupScript()`). |
| **Adopt** | The one-call action that turns a **Discovered LAN machine** into a registered **LAN server**: every registerable field — name, LAN address, Docker settings, device category — is derived from the discovered host, and the operator may optionally override only the name and optionally attach a **host credential**. The adopted host stops appearing as a discovered machine. Registration and the credential are separable: the machine is always registered, and the credential is re-verified and stored only when it authenticates — a rejected one never blocks the adoption. Distinct from the manual **register**, where the operator types the fields. |
| **Gateway peer** | (Planned, #174) A single peer designated to carry all internet traffic for opted-in clients. Distinct from a relay peer. |
| **LAN address** | The reachable IP (or hostname) of a server peer or LAN server on its local LAN — e.g. `192.168.1.50`. Used by the launchpad to hand out direct URLs. Editable inline via `PATCH /vpn/peers/{id}/lan-address`. Not the WireGuard tunnel IP. |
| **Machine id** | A machine's identity — an opaque, generated UUID that never changes and carries no meaning. Every machine has one, whatever kind it is: a **VPN peer**, a **LAN server**, or the **Vaier server** itself. Deliberately not derived from the **name**, the **LAN address**, or the **machine type** — anything derived from a mutable label is a label wearing an identity's clothes. Stored where the machine lives: a peer's **VAIER metadata**, `lan-servers.yml`, or the **Vaier config** for the Vaier server. Read, never minted — a machine whose stored id is missing or malformed does not load at all, rather than being silently given a new identity. Modelled by `domain.MachineId`, and carried by every **machine** projection. Distinct from the **peer id**, which is now only a storage key, and from the **name**, which is only a display label. |
| **Peer id** | A peer's WireGuard **storage key** — a slug (letters, digits, `_`, `-`) derived from the name the operator typed when creating the peer, deduplicated with a numeric suffix (`-2`, `-3`, …) when it would collide with an existing id. It is the WireGuard config directory name and the path segment of every `/vpn/peers/{id}` REST call, and never changes once assigned — not even on rename. Kept human-legible on purpose, so a fleet can be debugged from a console. Modelled by `domain.PeerId`. Not the peer's identity — that is its **machine id**. |
| **Name** | A machine's human-readable display label — what the UI shows, and nothing more. **Need not be unique:** two machines may wear the same name, because nothing is keyed to it (see **machine id**). For a peer it is operator-edited text; editing it changes only this label, never the **peer id** or the **machine id**. A peer with no stored name falls back to its **peer id** rendered with dashes as spaces. Distinct from the **machine id** (a machine's identity), the **peer id** (a peer's config directory) and the **description** (informational). |
| **Description** | Optional free-text label an operator attaches to a machine — a VPN peer or a LAN server — to record what it is, e.g. "Home media server (NUC, Ubuntu 22.04)". Purely informational, and distinct from the machine **name** (its display label). Carried under the name on the machine's card in the **Explorer**'s fleet listing, so what a machine is for is part of how the fleet reads. |
| **Rename** | Changing a machine's **name**. For a peer this edits the display **name** only — the **peer id**, its configuration, and its published services are untouched. The machine keeps its identity; only the label changes. Nothing else moves: a machine's **host credential**, **host-key pin**, backup jobs, disk watches and open **persistent shell**s all hang off its **machine id**, which a rename does not touch, so nothing is carried anywhere and nothing is orphaned. Distinct from deleting and recreating. |
| **Enrol** / **Enrolment** | How a phone running the Vaier app joins the fleet: the device mints its own WireGuard keypair, asks Vaier to hold the request as an **enrolment request**, and receives everything but the private key once an admin **approves** it from wherever they happen to be signed in — including the phone's own browser, when it is the operator's own device approving itself. The counterpart to creating a **peer**, where Vaier mints the keypair and hands it out; what it produces is an ordinary peer in every other respect, distinguished only by its **device-held key**. British spelling throughout — never "enroll". |
| **Enrolment request** | A phone that has minted its keypair and is waiting to be let in — anonymous, gated by its **join code** and **enrolment ticket** rather than a session, because the phone asking has none of its own yet. Carries the device's name and public key too, and lives ten minutes; at most five wait at once. Shown on the Explorer's fleet page as "Waiting to join" until it is **approved** or **refused**. |
| **Join code** | The four digits an **enrolment request** shows on the waiting phone and on the Explorer, so an operator can match a phone to a screen. Authorises nothing by itself — matching it is a human judgement, not a credential. |
| **Enrolment ticket** | 32 unguessable random bytes issued once to a waiting phone and never shown anywhere else. The only thing that gates delivery of a config to an **enrolment request** — distinct from the **join code**, which authorises nothing. |
| **Approve** / **Refuse** | The operator's two answers to an **enrolment request**, given from wherever they are already signed in. Approve admits the phone as an ordinary peer with a **device-held key** and delivers its config over the phone's own stream; Refuse turns it away, leaving no peer and no key behind. Either one ends the request. |
| **Leave** | A phone taking itself out of the fleet, proving it holds the config it was given — its own public key and the peer's preshared key — rather than any session. Offered only to a peer with a **device-held key**; a peer Vaier minted has no equivalent self-service exit. |
| **Standing** | Whether a phone is still a member of the fleet, answered only to a phone presenting the same proof as a **Leave** — and changing nothing. How the Vaier app learns it was removed: nothing pushes a removal to a phone, so when its handshakes stop it asks, and either reconnects or forgets itself and says so. |
| **Device-held key** | A peer whose private key was minted on the device and has never existed in Vaier. Such a peer has no downloadable artefact at all — no config, no QR code, nothing — because Vaier holds nothing the device does not already have. Recorded as the key's public half in the peer's **VAIER metadata**; its presence is what marks the peer. Neither a **Reissue** nor a **Regenerate** is offered for such a peer, and its config is never **out of date**: the key is replaced by removing the machine and enrolling it again, or the device removes itself via **Leave**. |
| **Peer config retrieval** | The act of downloading a peer's secret-bearing artefact (`.conf`, QR PNG, docker-compose, setup script). One-shot: the create response is the canonical delivery, and the five GET endpoints (`/config`, `/config-file`, `/qr-code`, `/docker-compose`, `/setup-script`) burn a shared budget — the first GET on any of them returns 200, every subsequent GET returns `410 Gone`. Tracked via a filesystem marker (`<peerDir>/<name>.conf.viewed`) and the `ForTrackingPeerConfigRetrieval` port. An **enrolment** spends the budget as it completes: the peer has a **device-held key**, so there is nothing left to retrieve. |
| **Setup token** | A single-use, short-lived (~15-minute), per-**machine** bearer token that is the sole authorization on a machine's anonymous **setup link** — a bare box being onboarded has no sign-in session, so the token stands in for one. Validated inside Vaier (`SetupToken.authorizes`, vended by `ForVendingSetupTokens`). Both a **server peer** and a **LAN server** use it; a server peer's is minted in the create/reissue response and redeeming it also burns the shared **peer config retrieval** budget (so an intercepted, already-spent link leaves the box unable to come up and the operator regenerates), while a LAN server's is minted on demand and its script bears no such secret, so the single-use token is the whole gate. |
| **Setup link** | The copy-and-paste one-liner an operator runs on a freshly-onboarded machine to bring it online — it fetches that machine's setup script over HTTPS from its token-gated setup route and runs it. Works exactly once. A **server peer**: `curl … /vpn/peers/{id}/setup?t=<`**setup token**`> \| bash` — writes the config and starts WireGuard in a container, no root. A **LAN server**: `curl … /lan-servers/{name}/setup?t=<`**setup token**`> \| sudo bash` — needs sudo because it installs Docker; offered from the adopt dialog and the machine's Setup-script control. |
| **Setup-script guard** | The block of refusals every generated **setup script** carries ahead of its first mutating line. A setup script reconfigures the machine it runs on, and Vaier delivers it as a **setup link** — a copy-and-paste one-liner — so the only thing keeping it off the wrong machine is which terminal the operator pasted into. The guard refuses when the host is a **Vaier server**, when the host is already stamped as a different machine (each completed setup records its machine name at `/etc/vaier/machine`), when a CIDR the script would route into the tunnel contains the address on the host's default-route interface (it would sever the host's own uplink), where Vaier knows the machine's address — when the host does not hold it, and — for a **LAN server**'s relay routes — when the host already runs a WireGuard client, since a machine is a peer or a LAN server, never both. Non-interactive by necessity, since the script arrives on stdin through a pipe; `VAIER_FORCE=1` is the deliberate override. Refusal exits 3 and changes nothing. |
| **Regenerate** | Operator action on a machine's pane in the **Explorer** that deletes the peer and recreates it with the same **name**/**peer type**/**LAN CIDR**/**LAN address**/**description**. Rotates the WireGuard keypair as a side effect of the recreate, which simultaneously clears the **peer config retrieval** marker and re-enables a one-shot delivery via the create-success modal. Used to replace a compromised config — the old config stops working immediately. Distinct from **Reissue**, which recovers a config without rotating the keypair (the non-destructive way to get a lost config back). |
| **Reissue** | Operator action that re-renders a peer's installable config from the *current* generation logic while **preserving its keypair and preshared key** — so the live tunnel and the server-side `[Peer]` entry are untouched — then persists the new config and re-opens the one-shot **peer config retrieval** budget so it can be delivered once more via the create-success modal. Used when generation logic has changed since the peer was created (e.g. the **server LAN CIDR** is now appended to server peers' client-side `AllowedIPs`) and an existing peer's config has fallen **out of date**. Unlike **Regenerate**, the operator must reinstall the reissued config on the peer machine for it to take effect. Refused for a **device-held key** — there is no installable config to re-render — with a sentence naming the machine and pointing at an **enrolment** instead. |
| **Rendered config** | The config the current generation logic would produce for a peer, with its keypair, preshared key, tunnel IP, and identity preserved — i.e. the output of a **Reissue**. Compared against the on-disk config to decide whether a peer is **out of date**. |
| **Out-of-date config** | A peer whose on-disk config differs from its **rendered config**. Surfaced as a badge in the peer list; cleared by a **Reissue**. |
| **LAN CIDR** | The IPv4 CIDR of the LAN sitting behind a relay peer — e.g. `192.168.1.0/24`. Recorded in the `# VAIER:` JSON header of the peer's client config and appended to the **server-side** `[Peer] AllowedIPs` only. Never appended to the client-side `AllowedIPs` (would hijack the relay's own LAN). The operator's answer, normally accepted from a **detected network** rather than typed. |
| **Detected network** | An IPv4 network Vaier read off a machine itself: the address the machine holds, the interface it was seen on, and the network that address sits on. An observation taken on the same scheduled sweep as the machine's **remote disk usage** and held only in memory — what Vaier last saw, never something an operator stated. Never one on a pseudo-interface (loopback, VPN tunnels, Docker bridges and the like), which could not be an operator's LAN. A machine's detected network is what Vaier offers as its **LAN CIDR**; the LAN CIDR is the answer, this is the reading behind it. |
| **Server LAN CIDR** | The IPv4 CIDR Vaier treats as "the network the **Vaier server itself** sits on". By default it's the server's own **subnet** CIDR, auto-**discovered** via EC2 IMDSv2 (`network/interfaces/macs/<mac>/subnet-ipv4-cidr-block` — a default-VPC subnet is a `/20`, one per AZ). `VAIER_SERVER_LAN_CIDR` is a general override (short-circuits IMDS, on EC2 too) — set it to widen the range, typically to the whole VPC CIDR (e.g. `172.31.0.0/16`) so machines in any AZ qualify, or to supply the value off EC2. Resolved by `ForResolvingServerLanCidr`; non-CIDR values are ignored; the result is memoized. A LAN server or LAN service whose address falls inside it is registered, scraped, and published directly from the Vaier-side containers (vaier / traefik → docker bridge → host → the host's LAN/VPC NIC) — no relay peer needed. Also appended to split-tunnel server peers' client-side `AllowedIPs` so they can *initiate* connections back into the server's subnet through the tunnel. Empty when undeterminable (the feature is then inert). |
| **VPN subnet** | The WireGuard /24 used for tunnel addresses (default `10.13.13.0/24`). |
| **Tunnel IP** / **WG address** | A peer's address inside the VPN subnet (e.g. `10.13.13.7`). Distinct from LAN address and endpoint IP. |
| **Tunnel identity** | Which **machine** a caller *is*, taken from its address — the one answer the tunnel, and only the tunnel, can give. A caller qualifies when its address sits inside the **VPN subnet** *and* is a peer's **tunnel IP**: WireGuard authenticated the packet, so the address cannot be forged. Both halves are the rule. Any other address — a carrier IP, a LAN address, the public internet — identifies a person and never a device, so it has no tunnel identity at all, and Vaier attributes nothing rather than guessing. The single rule behind **last service reached** and behind whose **reported position** a report is. Modelled by `domain.TunnelCaller`. |
| **Endpoint IP** | The peer's public IP as seen by the WireGuard server (`wg show dump`). The carrier IP for mobile/client peers. Used for geolocation. |
| **Latest handshake** | Unix epoch seconds of the most recent successful WireGuard handshake. Source of truth for connection state. |
| **Connected** | A peer is connected when `latestHandshake > 0` and `(now - latestHandshake) < 180s`. See `VpnClient.isConnected()`. Anything older is **disconnected** (which on the UI may render as "stale"). |
| **AllowedIPs** | WireGuard config field. Has both a **server-side** form (in `wg0.conf`'s `[Peer]` block on the Vaier server) and a **client-side** form (in the peer's own config). They are not interchangeable — see the LAN CIDR rules above. |
| **VAIER metadata** | The `# VAIER: {...}` JSON comment at the top of every client WireGuard config. Carries `id` (the peer's **machine id**), `peerType`, `lanCidr`, `lanAddress`, `description`, `name`, and — for a peer with a **device-held key** — `publicKey`. Every `update*` rewrites this whole line, so each mutator must carry every field — including `id` and `publicKey` — through. A peer whose metadata has no valid `id` does not load. Legacy peers without a `peerType` default to `UBUNTU_SERVER`; a peer with no `name` falls back to its **peer id** shown with dashes as spaces. |

Avoid: "node", "host" (ambiguous), "device", "client" by itself, "VPN node".

## 3. Service publishing

The primary workflow. Always use these terms — the UI is built around them.

| Term | Definition |
|------|------------|
| **Service** | (Without qualifier) a Docker container with at least one exposed port, running on the Vaier server or a server peer or a Docker-enabled LAN server. Discovered automatically. Backed by `domain.DockerService`. The **Explorer** files the same thing under a machine as one of its **containers** — one concept, and the word to use there is *container*, because in the Explorer "services" already means the machine's **published services**. |
| **Publishable service** | A discovered service eligible for publishing. Has a `source` indicating where it was discovered (`VAIER_SERVER`, `PEER`, `LAN_SERVER`). Surfaced as a **+ Publish** candidate row in its host machine's pane in the **Explorer**. |
| **Published service** | A service that has been wired through the publish flow: a Traefik route plus the middleware chain for its **auth mode** (public or social login), or — when the port is not a website — a **stream**. Its name resolves through the operator's **wildcard DNS** record, so publishing writes no DNS. Backed by a `ReverseProxyRoute`. Shown as a managed entry under its host machine in the **Explorer**. |
| **Stream** | A **published service** whose port does not serve a website: a Traefik TCP router matched by the host name in the TLS handshake (`HostSNI`) on the same HTTPS port every published service uses, with TLS terminated by Traefik under a per-hostname certificate and the decrypted bytes forwarded to the backend port unchanged. MQTT, a database, anything not HTTP. A stream's **auth mode** is always **none** and cannot be anything else — nothing inside it is an HTTP request, so neither the social-login chain nor the **CrowdSec bouncer** can act on it, and the service's own credentials are its only gate. It has no URL, so it takes no **path prefix** and no **root redirect**, and never appears on the **launchpad**. `ReverseProxyRoute.isStream()`. |
| **Connect address** | Where a client dials a **stream**: the published name and the HTTPS port, `<fqdn>:443`. A stream's counterpart to an HTTP service's **public address**, shown wherever that service would show a link. |
| **LAN service** | A published service whose backend is a host:port on a relay peer's LAN or in the Vaier server's own subnet (server LAN CIDR), not a container. `ReverseProxyRoute.isLanService == true`. Routed via the relay peer, or — when anchored at the Vaier server — straight from the Traefik container out the host's LAN/VPC NIC. Surfaces with a "LAN" badge; its host state follows the relay peer's tunnel, or is always OK for a server-anchored route. |
| **Publish flow** | The end-to-end pipeline: validate → write the Traefik route → confirm Traefik picked it up. The operator answers one question about the port itself — whether it serves a website or is a **stream** — and everything the answer makes meaningless is withheld. There is no DNS step — the name already resolves under **wildcard DNS**. UI shows it as a **Processing** card between Discovered and Active. Survives page refresh because state lives server-side. |
| **Unpublish** | Taking a **published service** down: its Traefik route is removed and it stops being reachable through Vaier. DNS is untouched — the name goes on resolving under the operator's **wildcard DNS** record, which is theirs and not Vaier's. The **backing container** keeps running — unpublishing is about how a service is *reached*, never about what runs it. The inverse of **publish**. |
| **Pending publication** | A publish in flight, tracked in-memory by `PendingPublicationsService`. Used to hide the source service from the discovered list and to reject duplicate submits. |
| **Publish rollback** | If the one remaining step fails — the Traefik route can't be written, or Traefik never picks it up — Vaier removes the route and emits a `publish-rolled-back` SSE event on the `published-services` topic. Traefik is the only thing that can trigger it now. |
| **Cleanup on machine deletion** | When a machine is deleted — a VPN peer or a LAN server — every published service whose backend address routes to that machine has its Traefik route removed too. No DNS is involved. |
| **Subdomain** | The label the operator picks at publish time. Combined with `VAIER_DOMAIN` to form the published service's DNS name. Held to what a DNS label is — lowercase letters, digits and inner hyphens, in dot-separated labels — because it is written into the routing rule that decides which traffic the service answers for. |
| **Mandatory subdomains** | `vaier` — the only subdomain reserved as Vaier infrastructure and barred from reuse as a published-service subdomain. Defined in `PublishingConstants.MANDATORY_SUBDOMAINS`. (`login`, the former Authelia portal host, is no longer mandatory.) |
| **Path prefix** | Optional `pathPrefix` on a published service (e.g. `/auth`). When set, the Traefik rule becomes `Host(...) && PathPrefix(...)` so multiple services can share one subdomain, each routed by path. Normalised by `ReverseProxyRoute.normalisePathPrefix` (blank/"`/`" → null; an operator-typed trailing slash is preserved verbatim — type `/auth` to match both `/auth` and `/auth/`, type `/auth/` to match only the slash variant). Route uniqueness is the `(fqdn, pathPrefix)` pair. |
| **Landing path** | The path segment a launchpad-emitted URL lands on. Decided by `ReverseProxyRoute` (`landingPath`, used by both `launchpadUrl` and `directUrl`): a non-blank `rootRedirectPath` wins; otherwise the `pathPrefix` is used verbatim; otherwise empty. So the operator's intended landing path is encoded either in `rootRedirectPath` (overrides everything) or in the slash they typed on the `pathPrefix`. |
| **Sibling routes** | Two or more `ReverseProxyRoute`s with the same FQDN, told apart by their **path prefix**. Nothing is shared between them beyond the name they answer on, which resolves through **wildcard DNS** like any other; each is published and unpublished on its own. |
| **Root redirect path** | Optional `rootRedirectPath` on a published service — appended to the direct URL and (where applicable) used for a Traefik redirect at root. Distinct from path prefix: path prefix decides *what requests reach this route*; root redirect decides *where bare `/` lands after routing*. Blank and `/` both mean **no** root redirect: Traefik's root rule matches the host with or without its trailing slash, so a redirect to the root re-matches its own trigger and loops. |
| **Direct URL** | The `http://lanAddress:port` URL the launchpad hands out *to callers on the same LAN* as the hosting peer, bypassing Traefik and its auth. |
| **Direct URL disabled** | Per-route opt-out (`directUrlDisabled`, persisted as `x-vaier-direct-url-disabled`). For services whose public origin differs from `http://lan:port` — Vaultwarden is the canonical case. |
| **Auth-mediated tile URL** | The URL the launchpad hands out for auth-protected services when no direct-LAN bypass applies, routing the browser through the auth gateway first so a PWA's service worker on the service origin can't serve a cached SPA that bypasses sign-in. |
| **Auth toggle** | Retired. The per-service on/off auth switch, superseded by **auth mode** (public or social login) — see §12. |
| **Hidden from launchpad** | Per-route operator switch (`hiddenFromLaunchpad`, persisted as `x-vaier-hidden-from-launchpad`). When on, the route is kept reachable but the launchpad never shows a tile for it. Use for internal APIs that back another service and don't need their own tile. Settable via `PATCH /published-services/{dnsName}` with `{"hiddenFromLaunchpad": ...}`. |
| **Offline page** | The branded, self-contained page Vaier serves in place of Traefik's default gateway error when a published service's backend is unreachable (502/503/504). Names the unavailable service, shows a friendly message, and offers a retry and a back-to-launchpad link. Backed by the domain `GatewayError` mapping (status → title + message). |
| **Offline fallback** | The always-up stand-in that shows a branded offline page for the Vaier host when the Vaier container *itself* is down — served by a separate tiny static server, not by Vaier, so the control panel degrades gracefully instead of showing "Bad gateway". |
| **Host-offline indicator** | Red dot on a launchpad tile (and, in the **Explorer**, the machine's own name in red — on its card and in its pane title; there is no dot) signalling that the machine hosting the service is confirmed unreachable. An *unknown* host (no probe data yet) gets a grey machine icon and a grey **pending** dot on its launchpad tile — distinct from "confirmed down". Fed by `ReverseProxyRoute.hostState(...)` → `Server.State.{OK,UNREACHABLE,UNKNOWN}`, which considers VPN handshake age (peer routes), relay-tunnel connectivity (LAN routes), and the LAN reachability probe (LAN routes). Never raised for DNS — under **wildcard DNS** a published name always resolves, so the host's reachability is the whole question. |
| **Presence** | Whether a personal device — a phone, laptop or PC, any **peer** that is not a server type — is on the VPN right now. Said by the machine itself in the **Explorer**, not by a dot: its name and icon read normally while present and dim while away, in the text greys and no trouble colour. Not a warning either way: a device that is off is not a server that fell over, so it never borrows the **host-offline indicator**'s red. A server that is fine still paints nothing. Read from the peer's **connected** state. |
| **Launchpad alias** | Optional operator-supplied tile label (`launchpadAlias`, persisted as `x-vaier-launchpad-alias` map). Overrides the default label when non-blank. Settable via `PATCH /published-services/{dnsName}` with `{"launchpadAlias": ...}` (empty string clears). |
| **Launchpad display name** | The label the launchpad tile shows. Computed by `ReverseProxyRoute.launchpadDisplayName(baseDomain)`: alias if set, else the final segment of `pathPrefix` for path-based routes (e.g. `/grafana` → `grafana`), else the first DNS label (e.g. `grafana.example.com` → `grafana`). The path prefix no longer leaks into the tile label as `subdomain/path` — the host appears on the tile's sub-line beside the peer when it differs from the display name. |
| **Icon lookup identity** | What the launchpad uses to ask `/icon` for an icon. Computed by `ReverseProxyRoute.launchpadIconQuery()`: host-only routes use just the FQDN; path-based routes carry `pathPrefix` too, so siblings under one host don't collide on the icon cache and the CDN-by-name fallback uses the path segment instead of the shared subdomain. The launchpad client renders `service.iconQuery` opaquely — it never decides what's in it. Doubles as the **icon cache key**, so the same identity addresses both the in-memory and on-disk caches. |
| **Icon** | A resolved service icon (`domain.Icon`): the image bytes plus the content-type the launchpad should report for them. |
| **Icon cache** | Where a resolved icon is remembered so it's fetched online at most once. Two tiers behind the same key: an in-memory map and a filesystem store (`ForStoringIcons`, default `/icons`) that survives restarts. Positives are persisted to disk; a "no icon found" result is remembered only in memory so a once-dead host can recover. |
| **Service origin** | Where a published service's backing process actually listens — `protocol://address:port`, read off its **route** (`ReverseProxyRoute.originUrl()`). Distinct from the service's **public address** (`https://<fqdn>`), which reaches the same process through Traefik and whatever **auth mode** the route carries. Anything Vaier fetches from a service *for itself* — its **icon**, its version endpoint — goes to the origin, since a **social-gated** service answers 401 to a request carrying no oauth2 cookie, and Vaier carries none. The origin is always read from Vaier's own route store, never accepted from a caller. A **stream** has an origin like any other route, but nothing Vaier fetches for itself is served over one. |
| **Ignored service** | A publishable service the operator has chosen to hide from the discovered list. Persisted via `ForManagingIgnoredServices`. |
| **Vaier's own stack** | The containers Vaier's `docker-compose.yml` starts on the **Vaier server** — Vaier, Traefik, WireGuard, oauth2-proxy, Dex, CrowdSec, the Docker socket proxy, the offline page and their sidecars. Distinct from the operator's own containers on the same host, which Vaier only discovers. |
| **Hidden container** | A container of **Vaier's own stack** that is never offered as a **publishable service** — it is Vaier's own plumbing, not something to publish. Decided by `domain.VaierServerCatalogue`. |
| **Offered container** | The carve-out: a container of **Vaier's own stack** that Vaier does offer for publishing, and only on the ports worth publishing. Today just Traefik's dashboard on 8080. |

Avoid: "expose", "deploy", "route" (as a verb for the user-facing publish action), "site", "endpoint" (ambiguous with WireGuard's endpoint).

## 4. DNS, reverse proxy, auth

| Term | Definition |
|------|------------|
| **Wildcard DNS** | The one `*.<domain>` A record, pointing at the **Vaier server**'s public IP, that the operator creates once at their own DNS host before the first boot. It is the whole of Vaier's DNS: it answers for the `vaier`, `oauth2` and `dex` infrastructure hosts and for every **published service**, and Vaier never writes to it. Provider-agnostic — any DNS host that can serve one wildcard A record qualifies. It answers for a name only while no more specific record in the zone claims a label above that name. Modelled by `domain.WildcardDns`. |
| **Wildcard DNS report** | What Vaier found when it checked **wildcard DNS** at boot: one of four verdicts — `COVERED`, `NOT_RESOLVING`, `RESOLVES_ELSEWHERE`, `UNCONFIRMED` — together with the plain-language sentence stating it. Modelled by `domain.WildcardDnsReport` / `domain.WildcardDnsStatus`; surfaced in the boot log and in Settings. |
| **Public host** | The Vaier server's public address as a `(value, type)` pair — either A (IPv4) or CNAME (hostname). Resolved by `ForResolvingPublicHost` in order: `VAIER_PUBLIC_HOST` → `VAIER_PUBLIC_IP` → EC2 IMDSv2 `public-hostname` → DNS lookup of `vaier.<domain>`. |
| **Reverse proxy route** | `domain.ReverseProxyRoute`. The Traefik-side half of a published service. Some routes are created by service publishing; others are added directly through the reverse-proxy CRUD endpoints (the escape hatch). |
| **Entry point** | Traefik concept: the named port a route binds to (`web`, `websecure`). |
| **TLS config** | Per-route TLS settings; `certResolver` names the ACME resolver in Traefik static config. |
| **Middleware** | Traefik chain element. A social-gated route carries the oauth2-proxy → Vaier authorization chain (`oauth2-signin`, `oauth2-authn`, `vaier-authz`); a public route carries none. The Vaier **console** relies on the same three middlewares, so Vaier keeps their definitions present in its generated config at every startup — not only when a social service happens to be published. A middleware can also be bound to an **entry point** rather than to a route, in which case every route on that entry point carries it: that is how the **security headers** reach every response. |
| **Forward-auth** | The Traefik mechanism where each request is forwarded to an external service before being passed upstream. Under social login the chain is oauth2-proxy (Google sign-in) followed by Vaier's own `/authz/verify` authorization check. There is no in-process Spring Security. A forward-auth **middleware** is not by itself an **auth middleware**: the same mechanism carries middlewares that authenticate nobody, such as a bouncer or a maintenance gate. |
| **Auth middleware** | One of the named Traefik **middlewares** by which Vaier authenticates a route — `oauth2-signin`, `oauth2-authn`, `vaier-authz`, the chain an **auth mode** puts in front of it. Membership of that named set is what makes a middleware an authenticator; using **forward-auth** is not, and neither is having "auth" in its name. |
| **Group** | A named set of identities used to gate who may reach protected services. In Vaier this is realised as an **access group** on an **access entry** (see §12); **access group** is the canonical term for the concept. |
| **ACME** | Let's Encrypt protocol for issuing TLS certs. `ACME_EMAIL` env var feeds the Traefik resolver. |
| **Edge security policy** | The security posture Traefik applies to every response it serves, independent of what any backend does. Comprises the **security headers**, the **frame guard** and the **edge TLS policy**. Rendered into Traefik's dynamic config at boot, in its own file alongside the one Vaier generates, and regenerated on every Traefik start — it is generated state, never operator state. |
| **Security headers** | `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`, added to every response on the `websecure` **entry point** — Vaier's own surfaces and **published services** alike. These two are the ones that stay safe on an application Vaier did not write. `Content-Security-Policy` is deliberately not among them: an application sets its own, per response, and a policy imposed at the edge would either overwrite it or intersect with it. |
| **Frame guard** | `X-Frame-Options: SAMEORIGIN`, carried by Vaier's own routers only — the console, the launchpad, the sign-in hosts and the **offline page**. Deliberately not a fleet-wide default: a **published service** may legitimately embed, or be embedded by, another site. `SAMEORIGIN` rather than `DENY` because the **Explorer** frames its own pages. |
| **Edge TLS policy** | Traefik's `default` TLS option set: a floor of TLS 1.2 and forward-secret AEAD cipher suites only (ECDHE with GCM or ChaCha20-Poly1305). Being named `default` it applies to every router that does not name its own, so it covers generated routes and Vaier's own alike. Not on the certificate-issuance path — the **ACME** HTTP-01 challenge is served over the plain `web` entry point. |
| **Trusted network** | The VPN subnet, the Docker bridge CIDR, every relay peer's **LAN CIDR**, and every **trusted address** as a single-host CIDR — the operator's own networks, which the fleet's threat-detection bouncer must never block. Modelled by `domain.TrustedNetworks`; rendered into CrowdSec's whitelist-parser file by `CrowdSecWhitelistFileAdapter`, refreshed on Vaier boot and on a recurring schedule (`TrustedNetworksScheduler`) — deliberately decoupled from any single VPN-peer action, since CrowdSec doesn't hot-reload the file either way. |
| **Block decision** | One active CrowdSec ban: the **source address** it names, the scenario that caught it, how long it lasts, and — when CrowdSec could place the source — where it came from (country, ASN organisation, coordinates). Modelled by `domain.BlockDecision`. ("Threat signal", CrowdSec's own word for the enriched alert a decision belongs to, is not Vaier vocabulary: the operator meets one thing, and this is its name.) |
| **Source address** | The single IPv4 address a **block decision** names — the address that knocked, and the only thing about a decision the operator can act on. Modelled by `domain.SourceAddress`: always one host, never a range. |
| **Lift a block** | Letting one blocked **source address** back in now. The only direction of a ban that is Vaier's to take — CrowdSec's own scenarios decide who is blocked, and Vaier never blocks anyone. One-off: the same address is blocked again the next time it trips a scenario. |
| **Trusted address** | A **source address** the operator has decided must never be blocked again. It joins the **trusted networks** as a single-host CIDR and is remembered, so it survives every rewrite of the allowlist. Where **lifting a block** is once, trusting stands — until the operator **untrusts the address**. The one part of the trusted networks a person chose, and the only part they can see or take back. |
| **Untrust an address** | Forgetting the operator's own decision to trust a **source address**, so it is judged on its behaviour again like any other. The inverse of making one a **trusted address**, and the other direction Vaier is allowed to take — it blocks nobody, since CrowdSec's scenarios are what decide that. Reaches only an address the operator trusted by hand: the rest of the **trusted networks** is structure, not a decision, and has no untrust. |
| **Blind scanning** | The kind of threat behind a **block decision** whose CrowdSec scenario is untargeted probing, crawling or vulnerability scanning — the internet rattling doorknobs it does not know are there. The overwhelming majority of what the edge blocks. Visible in the **Security view** and, when placeable, as a **threat ping**, and deliberately never emailed: a banned scanner is CrowdSec working correctly, and nobody can act on it. |
| **Credential attack** | The kind of threat behind a **block decision** whose CrowdSec scenario names somebody trying credentials — brute force, password spraying, an authentication endpoint. Distinguished from **blind scanning** not by severity but by whether the source picked this fleet: it is the one kind worth waking an admin for. Modelled by `domain.ThreatKind`, which reads the scenario's own name and treats anything it does not recognise as blind scanning. |
| **Breach attempt** | A **credential attack** on a source outside the **trusted networks**, that the operator hasn't been told about yet. `domain.BreachAttemptTracker` tracks which **block decisions** are newly appeared since the last sweep; `domain.BreachAttemptRollup` is the one-email-per-sweep notification for the ones that qualify. Most block decisions never become one. |
| **Lockout warning** | The alarm raised when a **block decision** names a source inside the operator's own **trusted networks**. Not a **breach attempt** and never reported as one: nobody is attacking, the allowlist has stopped protecting the operator's own traffic, and their access to Vaier itself is what goes next. Modelled by `domain.LockoutWarning`, with its own subject and body. |
| **Allowed access** | One request Vaier's **forward-auth** check let through. Everything Vaier gates counts one — a **published service**, the console, the **Explorer**, Settings. A denial is never one. Counted towards an **access source**. |
| **Access source** | A place **allowed accesses** have come from: its city and country, its coordinates when the **caller IP** could be placed, how many have come from there, when the first and the most recent one were, and the people allowed from there. Aggregated per place, not per address, so one entry stands for every request out of that city. A place the geolocation database could place but not name is still its own place, and reads by its coordinates. A **hairpinned access** is not a place and never opens one. Remembered for one month after its most recent allowed access, then forgotten; at most two hundred places are kept, the one seen longest ago going first. Modelled by `domain.AccessSource`, collected by `domain.AccessSources`. The mirror image of a **block decision** — who got in, rather than who was kept out. Not an **origin** (that is a block decision's country · ASN) and not an **access entry** (that is a person's permission, not a place). |
| **Last service reached** | The gated host a **machine** most recently reached through the **forward-auth** check, and when — the console and the **Explorer** count as much as a **published service**, since the same check gates them all. Shown against the machine, under the **launchpad display name** of the route serving that host when Vaier publishes one, and under the bare host when it does not. Known only for an **allowed access** that arrived over the tunnel, where WireGuard authenticated the packet and the **caller IP** is the **peer** itself; an access from anywhere else identifies a person and not a device, and is attributed to no machine at all. Modelled by `domain.LastServiceReached`, collected by `domain.LastServicesReached`. Not an **access source** (that is a place, and counts every allowed access) and not a **published service** (that is what was reached, not the reaching). |
| **Unplaceable access source** | The single **access source** standing for every **allowed access** whose **caller IP** has no place on a map — a private, VPN or LAN address, or a **hairpinned access**. It carries no city, country or coordinates, and is kept rather than dropped so the counts still add up. Named in its own right because "no location" is an answer, and silently discarding those accesses would make the total a lie. |
| **Hairpinned access** | An **allowed access** whose **caller IP** is the **Vaier server**'s own public address. A **client peer** runs a full tunnel, so its request to a gated service leaves through the Vaier server and returns wearing that address — which places the server, never the person. It has no place of its own and joins the **unplaceable access source**. Recognised only against an address Vaier has actually resolved; an unresolved one calls nothing a hairpin, so an access is never withheld from the **Map** on the strength of a lookup that has not happened. Modelled by `domain.ServerPublicAddress`. |

Avoid: "vhost", "site", "auth provider".

## 5. Discovery, reachability, status

| Term | Definition |
|------|------------|
| **Discovery** | The process of listing Docker containers on a host. `DiscoverVaierServerContainersUseCase` (Vaier server), `DiscoverPeerContainersUseCase` (server peer via `tcp://<peer>:<port>`), `DiscoverLanServerContainersUseCase` (LAN server, scraped through the relay — or directly from the Vaier container when the LAN server is in the server LAN CIDR). |
| **Reachability check** | A TCP probe (`ForProbingTcp`) used for LAN servers. Every 30s, hits ports 80/443/22; *any* response (handshake or RST) means pingable. If every TCP probe times out, an ICMP echo (`ForPingingHost`, backed by `/bin/ping`) fires as a fallback so printers / IoT / IPMI cards that don't expose any of those ports aren't falsely marked down. Drives the **machine status**. |
| **Machine status** | The four-state health of a machine (`domain.MachineStatus`), decided in the domain so the browser only picks a colour: `OK` (on the network, and any auxiliary scrape passed), `DEGRADED` (on the network, but its **LAN server scrape** is failing), `DOWN` (unreachable), `UNKNOWN` (no probe has run yet). `UNKNOWN` is not a healthy state and is never rendered as one — it is the absence of an answer, not an answer. |
| **SSH server presence** | Vaier's last-known belief about whether an SSH server is listening on a machine at all (`domain.SshServerPresence`: `UNKNOWN`, `PRESENT`, `ABSENT`) — distinct from **machine status**/**reachability check**, which answer "is the host on the network" and know nothing about SSH specifically. Recorded from the existing 5-minute disk-usage sweep (`RemoteDiskWatcher`) every SSH-accessible, credentialed machine already receives — never a second SSH round-trip — recognising a refused connect (`NoSshServerException`, the one signal narrow enough to trust) as `ABSENT` and any successful command run as `PRESENT`; every other failure (a timeout, a rejected credential) leaves it untouched rather than guessing. Read back at `GET /machines` and pushed live on the `vpn-peers` SSE stream (`ssh-server-presence-changed`) so the **Explorer** can grey out — never remove — the SSH-access checkbox, the machine's shell card, and its Files/Disk entries on a machine known to have nothing listening, lifting the greying the moment a later sweep reaches it again. |
| **LAN server scrape** | The 30s scheduled Docker-socket scrape of every Docker-enabled LAN server, owned by `LanServerScrapeService`. Status (`OK` / `UNREACHABLE`) is debounced with the same 3-cycle dampening rule as reachability so the icon doesn't flicker green↔yellow on a transient socket blip. The cached result is what `GET /docker-services/lan-servers` returns; on a confirmed status change it republishes the existing `lan-servers-updated` SSE event. The live `DiscoverLanServerContainersUseCase` is still used by the publishable-services flow, which needs current state. |
| **LAN scanner** | An on-demand, **asynchronous** sweep of a **scannable LAN** the operator picks — one **relay peer's** `lanCidr`, or the **server LAN CIDR** — that surfaces responsive hosts on it not yet registered as **LAN servers** (a targeted scan keeps the result small and quick; an unfocused sweep of every scannable LAN at once still exists). The probe is a narrow TCP-connect sweep over common service ports, run from the Vaier WireGuard container (which already routes to every relay LAN) via `ForScanningLan`; `LanScannerService` (`ScanLanUseCase` to start, `GetDiscoveredLanMachinesUseCase` to read) orchestrates it. `POST /lan-scan` starts a background scan (`202`); `GET /lan-scan` returns the snapshot (status + machines + last-completed); completion fires the `lan-scan-updated` SSE event. |
| **Discovered LAN machine** | One responsive host the **LAN scanner** found that is **not already registered** as any machine (LAN server or VPN peer): its address, an optional hostname, the open ports it answered on, and the **LAN anchor** it sits behind. Modelled by `domain.DiscoveredLanMachine`. Surfaced in the **Add a machine** flow's LAN-server branch — the operator picks *A LAN server* at the fork, picks which **scannable LAN** to scan (said as *via <name>*), sees the cached candidates for just that LAN instantly (live over the `lan-scan-updated` stream), and **adopts** the chosen one in one call: a single editable name over a read-only *Detected by Vaier* readout, with the SSH-access section shown only when the host actually listens on SSH (`sshAvailable()`), tested live before it is stored; a host that does not speak SSH is adopted without a credential. Also listed in the fleet's *Discovered on the LAN* section, whose *Add* opens the same adopt sheet. Not persisted — recomputed each scan. |
| **LAN host probe** | A targeted, single-host inspection of one LAN address the operator typed while adding a **LAN server** by hand — the manual counterpart to the **LAN scanner** sweep. Non-intrusive: it inspects only the one host already named, reporting whether it is reachable, the ports it answered on, whether it speaks SSH, whether it runs Docker, its guessed **device category**, and which **LAN anchor** routes to it — the same detected readout **adopt** shows for a scanned host. Not reachable — no anchor covers the address, or nothing answered — is a normal outcome, not an error. Modelled by `domain.LanHostProbe`. |
| **Guessed role** | An advisory classification of a **discovered LAN machine** from its open ports (`domain.LanMachineRole`: `DOCKER_HOST`, `WEB_UI`, `SSH_HOST`, `PRINTER`, `UNKNOWN`). Pre-fills the Add Machine hint only — never a hard fact. |
| **Probe result** | `CONNECTED` (open), `REFUSED` (host alive, port closed — still pingable), `UNREACHABLE` (timeout or low-level error). |
| **Four-state machine-icon colour** | The machine's status dot/icon in the **Explorer** — on its card in the fleet listing and in its pane title — paints only trouble: **yellow** (Docker host pingable but scrape failed) and **red** (host not pingable). Every other state — pingable and well, a client asleep, and not yet probed — draws nothing at all and takes no space either, so a healthy fleet carries no mark of any kind. A machine that is **down** says so by reddening its whole **card** and its name rather than by a dot the eye has to find, the dot standing down there since the card has already said it. The name is now historical: four states are still *decided*, but only two are *drawn*. The cost is deliberate and known — on the fleet listing an unprobed machine is indistinguishable from a healthy one, and the listing's "N online" count is the only place that gap shows. |
| **Field help** | The small visible "?" affordance next to an advanced form field whose hover text gives a one-line plain-language explanation (and example) of what the field does. |
| **Last seen** | Absolute timestamp shown in a machine's pane in the **Explorer**. Sourced from the latest WireGuard handshake for VPN peers; for LAN servers, the most recent successful TCP probe (CONNECTED or REFUSED). Preserved across later DOWN probes — once a host has been seen, the timestamp sticks until the LAN server is removed or the app restarts. |
| **Filesystem** | One mounted filesystem on a machine — its device, its **mount point**, its size, its free space, and how full it is. The unit Vaier reads, watches, judges and alerts on. A machine has several and they fill independently, so "the disk" on a machine is never one number. |
| **Mount point** | Where a **filesystem** is mounted on its machine (e.g. `/volume1`). Together with the **machine id** it is a filesystem's identity: the same mount point on two machines is two different filesystems, and two machines sharing a **name** are still two machines. |
| **Pseudo-filesystem** | A `df` row that is not really a disk: a kernel or in-memory mount (tmpfs, devtmpfs, proc, sysfs, cgroup, squashfs, overlay, aufs), or a bind-mount alias of a **filesystem** already reported (the `none` rows a Docker storage driver creates). Never read, never watched, never counted — reporting one would show the same disk twice and let a single volume raise two alerts. |
| **Disk alert threshold** | The **fleet-wide fallback** percentage of a **filesystem**'s capacity in use above which Vaier raises **remote disk pressure** (default 85%). Configurable in Settings. It applies to every filesystem whose **disk watch** does not carry a threshold of its own. It is the line pressure is raised at, not the line it is cleared at — clearing is a **recovery margin** below it. |
| **Disk watch** | Whether Vaier watches one **filesystem** on one machine, and at what threshold. Keyed on **machine id** and **mount point** together. It carries an optional threshold of its own, overriding the **disk alert threshold** for that filesystem alone. A filesystem nobody has configured is watched at the **disk alert threshold** — nothing is ever silently unwatched. Modelled by `domain.DiskWatch`. |
| **Muted filesystem** | A **filesystem** whose **disk watch** says Vaier does not alert on it — the one that is full by design, such as a fixed-size system partition that sits near-full forever. Still read and still shown; simply never judged. |
| **Remote disk usage** | A point-in-time reading of one **filesystem** on a machine, gathered by running `df` over SSH — for any machine in the fleet, including the Vaier host itself, reached via SSH-to-self like any other machine. Carries the machine, the device, the **mount point**, the filesystem's size, its free space, and the used percentage: a percentage on its own names nothing an operator can act on. Taken both on a schedule, to drive the disk alerts, and on demand, when an operator looks at a machine's disk — one command, one reading, one verdict. Modelled by `domain.RemoteDiskUsage`. |
| **Unreadable disk** | A machine whose **remote disk usage** could not be taken — the machine is asleep, the `df` failed or timed out, or its output yields no real **filesystem** at all. It is the absence of a reading, not a reading of zero and not a machine with nothing to watch: an unreadable disk is never a disk with room on it, and is never reported as a percentage. Modelled by `domain.DiskUnreadableException`. |
| **Remote disk pressure** | The condition where a watched **filesystem**'s **remote disk usage** is above the threshold its **disk watch** resolves to — the filesystem's own, or the **disk alert threshold**. A **muted filesystem** is never in remote disk pressure, however full it is. Applies uniformly across the fleet, including the Vaier host. |
| **Remote disk recovery** | The condition where a watched **filesystem**'s **remote disk usage** has dropped clear of its threshold by the **recovery margin** after having been in **remote disk pressure**. Merely dipping back under the threshold is not one: between the margin and the threshold the filesystem is still in remote disk pressure, silently. |
| **Recovery margin** | How far below its threshold a **filesystem** must fall before Vaier calls it a **remote disk recovery** — five percentage points, one **pressure band** wide. The hysteresis on the way down, mirroring the bands on the way up: without it a filesystem sawtoothing either side of its threshold would raise an alert and a recovery every cycle for a disk that never changed state. Between the margin and the threshold a filesystem raises nothing, and re-crossing upward is not a new alert. Not configurable. |
| **Pressure band** | How bad a **filesystem**'s **remote disk pressure** has got, in five-point steps: 80, 85, 90, 95, 100. It is the unit Vaier escalates on — a filesystem in pressure is alerted about once per band, and again only when it climbs into a higher one. Deliberately not a re-notification interval: escalation follows the disk getting worse, never the passage of time. Modelled by `domain.DiskPressureBand`. |
| **Notified band** | The **pressure band** the most recent **remote disk-pressure alert** for one **filesystem** went out at — what admins were last told about it. Held per filesystem, and only while that filesystem is in **remote disk pressure**: a **remote disk recovery** discards it, so a filesystem that recovers and re-fills is alerted about again from the lowest band. Slipping back down a band while still in pressure leaves it standing, and so does dipping under the threshold without clearing the **recovery margin**. Modelled by `domain.DiskPressureState`. |
| **Runway** | The projected time until a **filesystem** reaches **its own alert threshold** — not 100% — extrapolated from its **disk-fill trend** rather than from how it has moved in the last hour. The threshold, because that is the line at which the filesystem becomes the operator's problem, and the one **remote disk pressure** is declared at: the **disk-fill forecast** warns about crossing it, and the level alert takes over the moment it is crossed. A flat or draining filesystem has no finite runway, and neither has one already at or above its threshold — there is nothing left to count down to. Distinct from **remote disk pressure**, which is about the filesystem already being over the line rather than about when it will be. |
| **Disk-fill forecast** | A projection of one **filesystem**'s **disk-fill trend**: its current fullness, the threshold it is judged against, its fill rate, and its **runway** to that threshold. The fill rate is an amount of free space consumed over time — put to operators per day, as `1.2 GiB/day` — never a percentage of capacity, which is too coarse a thing to measure a slow fill by. Trend-based ("will cross its threshold"), as opposed to the level-based **remote disk pressure** ("has crossed it"). |
| **Disk-fill trend** | The retained history of one **filesystem**'s free space — about a week of readings, at most one an hour — that its **disk-fill forecast** is projected from, together with whether admins have already been warned that this filesystem is heading for its threshold. Kept per filesystem and outliving a restart, because a projection measured in days cannot be built from readings that live only as long as a process. Modelled by `domain.DiskFillTrend`, one reading per `domain.DiskFillSample`. |
| **Forecast horizon** | The fixed seven-day **runway** below which a **disk-fill forecast** warrants an early warning — seven days of notice before the **filesystem** reaches its **disk alert threshold**, not before it is full. A warning already raised is called off only once the runway rises clear of a wider margin, so a filesystem drifting either side of the horizon is not repeatedly warned about and cleared. Unlike the **disk alert threshold** it names, it is a constant, not configurable. |
| **Machine disk standing** | The worst thing true about one machine's watched **filesystem**s right now: which of them is closest to the threshold it is judged against, how full it is, that threshold, how many of the machine's watched filesystems are in **remote disk pressure**, and how many were read and judged. Its severity is `CLEAR`, `CLOSING` — the worst filesystem is within one **pressure band** of its threshold — or `BREACHING` (`domain.DiskStandingLevel`). Closest to trouble is not fullest: a filesystem judged against a generous threshold of its own can be fuller than the one that counts. A **muted filesystem** is never counted and can never be the worst one, so a machine with every filesystem muted has no standing at all — and neither does one Vaier has not read yet. An absent standing is the absence of a reading, never a machine whose disks have room, and there is deliberately no unknown severity to say otherwise. What Vaier last saw, held only in memory, and retained from *every* reading of the machine's **remote disk usage** — the scheduled sweep's and an operator's look at the machine's filesystems alike. A reading that failed leaves it untouched: not knowing is not the same as nothing to judge. Modelled by `domain.MachineDiskStanding`. |
| **Capability strip** | The small glyphs marking the capabilities an operator scans the fleet for, in the order reached → runs → keeps: a relay glyph when it is a **relay peer**, a Docker glyph — wearing Docker's own blue, the one borrowed identity in the strip — when the machine runs Docker, and a safe glyph when it is the fleet's **backup server**. The rest stay deliberately dim: the strip says what a machine *is*, and colouring all of it would put it in competition with the **machine marks** that carry a verdict. It rides on the machine's card in the fleet listing, beside its name in the card's top row — a thing of its own, not one of that machine's **machine marks**, which sit apart, beneath the description. The safe is deliberately not the machine's device shape (the NAS already wears that because it *is* a NAS, and any machine can be designated) nor the **backed-up shield** (which says the opposite — that a thing is stored, not that it stores). A machine with none gets an empty strip so names still line up. |
| **Machine marks** | What a machine says without being opened: chips on a line of their own beneath the description on its card in the **Explorer**'s fleet listing — distinct from the **capability strip**, which rides beside the name instead and says what the machine *is* rather than a verdict. Each mark pairs a coloured glyph with a short word, the fuller sentence still held on the chip's title for whoever hovers: how its last **backup run** went ("Backed up" in the backup's own aqua while the last run kept everything, "Backup failed" in amber or red once it did not, never a second **status dot** — one bare coloured dot beside the liveness dot could mean either); its **machine disk standing** ("Disk has room" in the disk's own violet while there is room, "Disk 91% full" in amber or red once there is not, the percentage said only when it is not clear, naming the worst **filesystem** and the threshold it is judged against on the title — a machine with no standing gets no mark at all); its **Claude sign-in standing** ("Claude signed in" or "Claude signed out" in Claude's own clay — the same colour either way, the chip worn hollow when signed out, because the colour says whose sign-in it is and the weight says whether anyone holds one; amber and red belong to trouble wherever it appears, and a sign-in is presence rather than an outage — naming the **Claude account** and the **effective user** it is about on the title — and drawn for those two answers alone, since none of the quiet ones is a verdict worth marking); and how many of its containers are **update available** ("3 updates"). One rule runs through them: a mark's colour says *what it is about* — the backup's aqua, the disk's violet, Claude's clay — and the word beside it stays neutral; only trouble recolours the whole chip, amber or red with a tinted ground, so those two are never spent on anything but trouble. The green they used to share is gone from Vaier altogether: the **status dot**s that kept it have stopped drawing their healthy state too, so green now says nothing anywhere and only trouble speaks. What a machine nobody is looking at is saying, said where the fleet is listed. Absent while the Explorer is showing the past, since these are facts about the present. |
| **Back up (the verb)** | The **Explorer** selection bar's one intent: protect what is ticked. Everything mechanical behind it is Vaier's — it gets-or-creates the machine's **backup repository** on the **backup server**, gets-or-creates its **backup job**, folds the selection into the job's paths, and on a **first back-up** readies the host (**Prepare client** + key trust). The operator states intent; Vaier decides mechanism. It is offered **only while the fleet has a backup server**, and never on the backup server itself: with none designated there is nowhere to put an archive, so rather than being offered and then refused, the verb is absent until **designate backup server** has been answered — the one decision in this flow Vaier cannot make for the operator. |
| **Geolocation** | `GeoLocation(latitude, longitude, city, country)` resolved by `DbIpGeolocationAdapter` against a DB-IP City Lite MMDB downloaded by the `geoip-init` container. The lookup itself, from an address to a point — what it is a geolocation *of* is what decides whether it says anything about a device: see **ISP estimate**. |
| **Map** | The fleet-root map entry in the **Explorer**: a self-hosted Leaflet/OpenStreetMap world map with markers and clustering, plotting each machine at its **placement**, every place an **access source** could be placed as a green dot, and every placeable **block decision** as a **threat ping**. A green dot is somewhere a person was, never somewhere Vaier's own traffic turned around: a **hairpinned access** draws none. A machine's **position trail** is drawn for one machine at a time — whichever machine's marker popup is open — so the fleet's own picture stays readable. A machine with no placement is not drawn — the map shows where Vaier knows machines are, never where one last appeared to be. A child of the fleet, offered on the fleet's own listing as a second way of looking at the same machines rather than as another machine. There is no separate "List tab" — machines are **entries** of the fleet. |
| **Server marker** | The single distinct marker for the Vaier server itself on the **Map**. |
| **Threat ping** | The **Map**'s marker for a **block decision** CrowdSec could place — a radar-style contact, deliberately unlike any machine's marker and drawn on a layer of its own, because a blocked address is not part of the fleet. |
| **Mobile/client dual marker** | A Mobile/Windows-client peer plots twice: a marker at its **placement** plus a firm marker stacked at the **Vaier server**, reflecting `AllowedIPs = 0.0.0.0/0` full-tunnel routing. The first marker is drawn dotted when the placement is an **ISP estimate** and firm when it is a **reported position**, and is absent altogether when the peer has no placement. |
| **Reported position** | The coordinates a device's own browser gave via the W3C Geolocation API — latitude, longitude, accuracy in metres, and the instant it was taken. Held per **machine id**, never by **name** or tunnel IP, both of which are mutable labels. The only evidence Vaier has that is actually about a device rather than about its carrier. It persists until the device is forgotten — there is no expiry, only ageing, so a **placement** goes stale rather than disappearing — and it lives in the **Vaier config** directory, which means it lands in whatever backs that directory up. Someone's whereabouts, kept until they say otherwise. Modelled by `domain.ReportedPosition`. |
| **ISP estimate** | The **geolocation** of a **VPN peer**'s endpoint IP: a carrier's registry point, not evidence of where a device is. A whole mobile block commonly resolves to one address — the carrier's head office — so an ISP estimate can be precise, current, and still hundreds of kilometres from the phone. Replaces the older UI wording "approx. ISP location". |
| **Placement** | The decided answer to "where is this machine": the coordinates, which evidence they came from (**reported position** or **ISP estimate**), when that evidence was taken, and whether it has gone stale — past 24 hours old. Absent whenever Vaier has no honest answer, notably for a **VPN peer** that is disconnected and has never reported: WireGuard keeps naming the last endpoint it saw, and a day-old carrier address is not a location. A reported position always wins over an ISP estimate, even a fresher one; age is shown rather than allowed to promote the coarser source. Modelled by `domain.Placement`. |
| **Position trail** | Where a machine has been: the **reported position**s it sent that were worth keeping, oldest first. Built from reported positions alone — an **ISP estimate** never joins one, because a carrier's whole address block resolves to a single point and a journey drawn from those would be a line from the carrier's head office to itself. Not every report joins it: a point is kept only when it is meaningfully newer or meaningfully elsewhere than the last one kept. Bounded twice — 30 days, and a hard ceiling on how many points one machine holds, the most recent kept when it is reached. Where a machine *is* and where it has *been* are two different answers, and a trail is only ever the second. Forgetting a device takes its whole trail with it, and a report still in flight when that happens starts no new one. Modelled by `domain.PositionTrail`. |
| **Device claim** | A binding between one browser and one **machine id**, letting that browser record the machine's **reported position** from anywhere, tunnel or not. Made once from an authenticated console session, carried afterwards as an opaque cookie token Vaier issues and checks against its own stored record — deliberately not a self-contained signed blob, which could not be revoked. Revoking it is what makes forgetting a device actually forget it. Revocation takes effect at once: a **reported position** already on its way is refused rather than recorded, because which machine is reporting is decided against the claims Vaier holds now, never against a copy read a moment earlier. A property of the browser holding it, not of the machine: a machine is never described as claimed to anyone but the browser that claimed it. Modelled by `domain.DeviceClaim`. |

## 6. Launchpad

| Term | Definition |
|------|------------|
| **Launchpad** | The public, **viewer-adaptive** dashboard at `/launchpad.html` showing published services as a tile grid. Suitable as a browser home page. An anonymous visitor sees only public services; a signed-in **viewer** additionally sees the social services it may reach. Admin pages remain admin-only. Reads are pure — the launchpad never creates or mutates an access entry. |
| **Tile** | A single service card on the launchpad — service name, peer name, icon, link, and, on hover, the Docker image and running version of the service behind it. |
| **Caller on host LAN** | Whether the launchpad's caller is browsing from the same LAN as the machine hosting a tile: the **caller IP** is the tunnel endpoint IP of the hosting **peer** (or, for a **LAN service**, of its relay peer). The fact behind a **direct URL**, but held even where the direct URL is disabled or the peer has no **LAN address**. The launchpad lists the sections of the machines the caller is with ahead of the rest, so at home the home server's services come first. `ReverseProxyRoute.callerOnHostLan(...)`, carried on the tile as `callerOnHostLan`. |
| **Backing container** | The Docker container that serves a published service. Its image and version are surfaced on the launchpad tile and on the published-service entry in the **Explorer** (`Version`), resolved by `ReverseProxyRoute.backingContainer(...)` against discovered peer / Vaier-server / LAN-server containers. A service published as a bare LAN host:port has no backing container. |
| **Version endpoint** | An operator-configured URL and property name on a published service. Vaier reads the service's running version from that URL and shows it on the tile and on the published-service entry in the **Explorer** — used for a service that has no backing container, such as one running natively on a LAN machine. |
| **Launchpad visibility** | Tri-state outcome the domain computes for each route (`domain.LaunchpadVisibility`): `NOT_VISIBLE` (operator hid it, or a social-gated route the viewer may not reach — anonymous, pending, or a user outside the allowed groups — no tile rendered), `VISIBLE_INACTIVE` (tile shown but de-emphasised — backend currently unreachable), `VISIBLE_ACTIVE` (tile shown normally). DNS is no longer one of the inputs: under **wildcard DNS** a published name always resolves, so DNS can never hide a tile. Owned by `ReverseProxyRoute.launchpadVisibility(hostState, AccessEntry viewer, ForResolvingServiceGroup serviceGroups)` (with `isVisibleToLaunchpadViewer(viewer, serviceGroups)` deciding whether a tile appears at all); new launchpad-visibility rules accrete there rather than in the application layer. |
| **Launchpad tile liveness** | Presentation tri-state (`domain.LaunchpadLiveness`) for a launchpad tile's status dot, reporting host reachability alone and separate from launchpad visibility (which governs the tile's link and dim): `LIVE` (green — host confirmed reachable), `PENDING` (grey — reachability not yet confirmed, e.g. at startup before the first probe), `OFFLINE` (red — host confirmed unreachable). A service counts as "online"/"reachable" only when `LIVE`. |
| **Caller IP** | The address a request really came from — the launchpad visitor whose direct URL is being decided, and the person whose **allowed access** is being recorded. Taken from `X-Forwarded-For`, leftmost hop, only when the immediate connection is from inside the **trusted proxy CIDR** (default `172.20.0.0/16`); otherwise from `RemoteAddr`. Which hop to believe is a decision, so it is the domain's: `domain.CallerIp`. |
| **Viewer** | The identity looking at the launchpad — either anonymous (`null`) or a resolved **access entry** — that the launchpad adapts its tiles to. An anonymous viewer sees only public services; a signed-in viewer additionally sees the social services it may reach. Resolved read-only from the signed-in email (`ResolveViewerUseCase`); a pending or unknown identity resolves to no extra access. |
| **Identity-optional router** | The middle launchpad routing tier that injects a signed-in identity's headers when a session exists but never forces sign-in and never gates on admin — so a signed-in non-admin can read its own identity and its own reachable tiles, while an anonymous request is refused and the page falls back to the public feed. Distinct from the public tier (no auth at all) and the admin catch-all (full sign-in + admin gate). |
| **Trusted proxy CIDR** | The CIDR Vaier trusts to set `X-Forwarded-For`. Default is the Docker bridge subnet. Set by `vaier.trusted-proxy-cidr`; the older `launchpad.trusted-proxy-cidr` is still read where that is unset. One value for both the **launchpad** and the **forward-auth** check, which ask the same question. |

## 7. Lifecycle, setup, notifications

| Term | Definition |
|------|------------|
| **Lifecycle** | `domain.Lifecycle`. The boot sequence: check the operator's **wildcard DNS** record and state the **wildcard DNS report**. Vaier creates no records — DNS is the operator's one record, so boot verifies it rather than writing it. |
| **First-run** | The first `docker compose up -d` on a host. Triggers the `geoip-init`, `vaier-init`, `oauth2-proxy-init`, and `dex-init` one-shot containers, seeds the **configured administrator** into the access store, ensures the console's own social auth **middlewares** exist in the generated Traefik config so the operator can sign in even before any service is published, and states the **wildcard DNS report** for the record the operator created beforehand. |
| **Docker socket proxy** | The `tecnativa/docker-socket-proxy` sidecar (`docker-proxy` container) that holds the real `/var/run/docker.sock` and exposes a restricted HTTP API on `tcp://docker-proxy:2375` over `vaier-network`. Vaier and Traefik talk to it instead of mounting the host socket. Allowlist: `CONTAINERS, EVENTS, EXEC, IMAGES, PING, POST, ALLOW_RESTARTS`. Default-deny on `/containers/create`, `/containers/{id}/start`, image pulls, swarm/network/volume management. |
| **vaier-init** | One-shot busybox container that `chown`s the bind-mounted config dirs to UID 1000 on every start, so the non-root Vaier process can read and write its own state. |
| **SMTP notifier** | The Jakarta Mail-based outbound mail integration. Powers Vaier's admin alert emails. Settings and the password live in `vaier-config.yml`. |
| **Test email** | A full AUTH + roundtrip Jakarta Mail send triggered from Settings, used to verify SMTP config independently of the auth layer. |
| **Machine transition** / **up/down alert** | Email sent to every **admin**-role **access entry** when a server-type machine (VPN server peer or LAN server) flips connected/disconnected. Mobile/Windows clients are excluded — their disconnects are routine. The first observation after Vaier startup is treated as a baseline so restarts don't generate noise. |
| **Remote disk-pressure alert** | Email sent to every **admin**-role **access entry** about a watched **filesystem** in **remote disk pressure**: on the first observation of it in pressure — including the very first observation Vaier ever takes, so a filesystem already full when Vaier starts is not silent — then again each time it climbs into a higher **pressure band**, with a paired recovery email on **remote disk recovery**. It names the machine, the **mount point** and the filesystem's size and free space, never a bare percentage. Never repeats within a band, never fires on a timer, and never pairs an alert with a recovery for a filesystem that only dipped back inside the **recovery margin**. This is the sole disk-alert path — it covers every real filesystem of every SSH-accessible machine Vaier holds a **host credential** for, including the Vaier host itself (reached via SSH-to-self, same as any other machine). A machine that is unreachable or whose `df` fails is skipped rather than alarmed. Superseded an earlier, separate local-host-only disk-pressure alert, which was retired once this alert could reach the Vaier host itself, to stop double-notifying admins for the same host. |
| **Disk-fill early-warning alert** | Email sent to every **admin**-role **access entry** when a **filesystem**'s **runway** first drops below the seven-day **forecast horizon** while it is still below its threshold — about a week's notice that it is heading for that threshold, named in the mail. It says the filesystem is projected to *reach its threshold*, never that it is projected to be full: the two are weeks apart on a slowly filling disk, and the threshold is the one Vaier will act on. It is paired with an all-clear only on a genuine recovery: the filesystem drained, or its fill slowed so far that the runway rose clear of the horizon's wider all-clear margin, all while still below the threshold. A runway grazing back over the horizon is not a recovery and raises nothing. Names the **mount point** it means. Trend-based counterpart to the level-based **remote disk-pressure alert**: a filling filesystem raises this once, then hands off to the pressure alert when it crosses the threshold — that hand-off raises no all-clear (the pressure alert speaks for it), so admins are never paged twice for the same filesystem. |
| **Access-request alert** | Email sent to every **admin** when a new **pending** **access entry** is created — i.e. when an identity signs in for the first time and lands awaiting approval. The mail names the email and points the admin to the access overview to approve or deny it. Fires only on the first sighting, never on repeat sign-ins by the same pending identity. |
| **Nudge** (progressive-adoption nudge) | An evidence-backed, single yes/no suggestion Vaier surfaces on a **machine** to adopt one more of its capabilities — carrying a title, the **evidence** (the "why", drawn from already-cached state) and the action taken on "yes". Not an alert: it is shown in the UI on the machine, never emailed. Five kinds: **publish** (the machine exposes services not yet routed through Vaier and not already dismissed as an **ignored service** — dismissing one answers this nudge), **back-up** (the machine is reachable and credentialed with nothing backed up yet), **designate backup server** (the fleet has no **backup server** yet and the machine is storage-class), **back up as root** (the machine's latest **backup run** is an **incomplete backup** whose **unreadable files** were denied on permissions, and its **backup job** does not already **back up as root** — the lost files themselves are the evidence), and **route LAN** (the machine could be a **relay peer**, has no **LAN CIDR** yet, and Vaier holds a **detected network** for it — the machine and the interface it was read from being the evidence). Each kind's "does it apply?" is a domain decision; a kind that does not apply raises no nudge. |
| **Registry** | The container-image host an image is pulled from — Docker Hub, `ghcr.io`, `lscr.io`. Any Registry v2 host, read anonymously; Docker Hub is one of them, never the assumed one. |
| **Image digest** | The registry digest of the image a container actually runs, as its host reports it. Not the image id (a config sha, which no registry serves). |
| **Registry digest** | The digest a **registry** currently serves for a given image's tag. The other half of the comparison **update available** is decided by. |
| **Scoped image** | An image as it runs on one particular **machine** — the unit Vaier tracks for **update available**. The same tag may run on the **Vaier server** and on several peers at once; scoping the verdict to a machine is what lets an alert name which host to act on, and what lets the same tag read **update available** on one machine and **up to date** on another (each container's own **image digest** is compared, against the one shared **registry digest**). Modelled by `domain.ScopedImage`; its label reads e.g. `vaultwarden/server:latest on Apalveien 5`. The **registry** is still asked once per distinct image string, never once per scoped image. |
| **Update available** | Vaier's verdict on a **scoped image** when its **registry digest** differs from its **image digest** for the same tag: the registry serves a newer image than the container runs. One of three verdicts, alongside **up to date** and **unknown**. Never an instruction Vaier acts on — Vaier does not pull or restart. The Explorer marks such a container with a yellow mark in its machine's container list, and counts them on the machine's card; the mark is advisory (nothing is broken) and names the operator's own action, never Vaier's. |
| **Up to date** | Vaier's verdict on a container's image when its **registry digest** and **image digest** are the same. |
| **Unknown** (update verdict) | Vaier's verdict on a container's image when it cannot compare the two digests — the registry is unreachable or rate-limited, the image was built locally and has no **registry digest**, the image is pinned to an exact digest, the container has just been **updated** and no sweep has yet judged what it now runs, or the container belongs to **Vaier's own stack**, which is never swept. Distinct from both **update available** and **up to date**: it means unknowable, never either answer. The Explorer draws no mark for it, so the absence of a mark means either **up to date** or **unknown** and is not a claim that an image is current; a container's Inspector names the verdict in words to carry that difference. |
| **Update sweep** | The daily pass in which Vaier asks each **registry** for the current digest of every running container's image and settles each one's verdict. A sweep that moved any verdict pushes it to open **Explorer**s, so a mark appears when Vaier learns it rather than on the next reload — the same push, on the same decision, as an operator's own **update check**. **Vaier's own stack is not swept** — those images move with a Vaier release, so a verdict on one is an alert nobody can act on; they are dropped before any registry is asked, so they spend no rate limit either. The same container name on a **VPN peer** or **LAN server** is the operator's and is swept as normal. |
| **Update check** | An **update sweep** the operator asked for rather than the daily schedule, from **Check the registries now** in the Explorer. Fleet-wide, and always fresh: it re-reads the containers and refuses every remembered **registry digest**, so it can never answer from before the operator's pull. It mails admins whatever it newly finds **update available**, exactly as the daily sweep would, so the mail leaves with the mark and the sweep that follows has nothing to add. Read-only like the rest of **update available** — it checks, it never pulls. |
| **Update check floor** | The minimum interval between two **update checks**. A check inside it is **coalesced**: Vaier asks nothing and reports when it last really looked, rather than claiming to have checked. |
| **Moving tag** | An image tag Vaier has seen move to a new **registry digest** twice running, each change within about a day and a half of the next and the last of them that recently — a nightly or edge channel rather than a settled release. A moving tag still earns the **update available** mark in the **Explorer**, named there with one muted word, and never raises an **update-available alert**. Two changes and not one, because one change is what a settled tag looks like when it cuts a release. A tag stops being moving once that long passes without another change, so a channel that goes quiet, and a release cadence measured in weeks, are both mailed as normal. Judged per image string rather than per **scoped image** — a registry answers about a tag, not about a host — from the digests remembered in `update-available.yml`. Modelled by `domain.RegistryDigestHistory`. |
| **Update-available alert** | Email sent to every **admin**-role **access entry** naming the **scoped images** that have newly become **update available** — each named as the image *and the machine it runs on* (e.g. `vaultwarden/server:latest on Apalveien 5`), so the operator can tell which host to act on. One mail per **update sweep**, however many it names. Sent once per image and not again while it stays out of date — including across a restart of Vaier, since the verdicts it has already sent are remembered in `update-available.yml`. Deliberately unlike the **remote disk-pressure alert**, whose very first observation after a restart does speak: a full disk is worth hearing about again, an image the operator has already been told is stale is not. Never sent for a **moving tag**, whose change is recorded without being reported, so the silence ends at that tag's next news rather than with a backlog. |
| **Compose coordinates** | How Docker Compose started a container: the compose **project** it belongs to, the **service** it is within that project, every compose file the project was defined by, and the directory compose ran in. Docker records all four on the container itself as labels, so a compose-managed container carries its own address. A container started by hand with plain `docker run` has none, and one whose labels do not survive validation has none either — they are metadata a container states about itself, so they are read as untrusted. Modelled by `domain.ComposeCoordinates`. |
| **Update** (a container's image) | Recreating one container on the newer image its **registry** now serves, from its own **compose coordinates**, so the service comes back exactly as it was defined. The operator's action on an **update available** verdict. **One word, two concepts, told apart by a single rule: the act is bare "update", the verdict is always "update available".** The act is a verb Vaier carries out on request; the verdict is only Vaier's reading of two digests and is never an act. Where a bare noun would be ambiguous, the verdict takes the longer name. An update that succeeds **forgets** the remembered verdict for that container's **scoped image** rather than claiming **up to date**: Vaier pulled and recreated, it did not re-compare the digests, so the honest reading afterwards is **unknown** until the next **update sweep** or **update check**. An update that succeeds also removes the image it replaced, on that machine. |
| **Update eligibility** | Whether Vaier may offer to **update** a container's image at all, and the plain reason when it may not: **updatable**, **not compose-managed**, **Vaier's own stack**, or **no Docker access**. Decided per container against the machine it was scraped from, because a container's name alone cannot say whose it is — a **VPN peer** or **LAN server** running its own `traefik` or `redis` is the operator's container. Modelled by `domain.ContainerUpdateEligibility`. |
| **Docker command access** | Whether the user Vaier signs in as on a machine can drive Docker there — a fact about the **machine**, not about any container on it. Vaier cannot infer it from anything else it knows: the container **discovery** reads Docker's API over the tunnel and needs no Unix group, so a machine whose SSH user is outside its `docker` group scrapes perfectly while every command an **update** would run there is refused. Learned on the disk sweep's existing trip, held in memory as what Vaier last saw, and re-read every sweep so a fixed group heals itself. Three states: granted, refused, and **unknown** — which is not a no. Modelled by `domain.DockerCommandAccess`. |
| **No Docker access** | The **update eligibility** of a container whose machine's **Docker command access** is refused. The action is withheld with the remedy named rather than offered and left to fail: catching it here is the difference between a button that cannot work and five failed updates in a row. A machine nobody has swept yet is **unknown**, never refused, so the action stays on offer until Vaier has actually looked. |
| **Not compose-managed** | The **update eligibility** of a container Vaier holds no **compose coordinates** for. Vaier does not know how it was started, so it will not recreate it: an update that silently drops a container's configuration is worse than no action offered. |
| **Update outcome** | How an **update** ended, and the sentence the operator is shown for it: **updated**, **pull failed**, **recreate failed**, **timed out** or **unreachable**. The pull and the recreate are read separately so the two failures stay distinct — in both, and in **unreachable**, the old container is still running, which is the good ending of a bad update and is said rather than reported as a generic error. Every outcome but **updated** carries an **update diagnostic** wherever the host gave one, so the operator is told *why* and not only *what* — added to that reassurance, never in place of it. Modelled by `domain.ContainerUpdateOutcome`. |
| **Update settlement** | How an **update** ended once it was carried out: its **update outcome**, and — whenever it did not end well — the **update diagnostic** explaining why. Modelled by `domain.ContainerUpdate.Settlement`. |
| **Update diagnostic** | The host's own words about why an **update** did not succeed: the failing command's last meaningful line, reduced to one printable, length-bounded line so it can be shown to the operator and written to the log without carrying a host's whole output. Absent when there is nothing to explain (the update worked) or nothing was said (the command failed silently). |
| **Updated** | The **update outcome** in which the newer image was pulled and the container was recreated on it. The only outcome that is a success, and the only one that retires the container's remembered **update available** verdict — every other outcome leaves the old image running, so the mark it earned is still true. The only outcome that removes the **replaced image**, for the same reason. |
| **Replaced image** | The image a container ran before it was **updated**, removed from that machine by digest once the update succeeded — otherwise every update leaves an untagged image behind, which on a **moving tag** is one abandoned image per update on a disk Vaier itself raises alerts about. Exactly that one image and nothing else: no sweep of a machine's unused images, and no force, so Docker's refusal to remove an image another container still runs stands. A removal that is refused or fails leaves the outcome **updated** and is written to Vaier's log, never added to what the operator is told — housekeeping that did not happen is not an update that failed. Nothing is removed after any other **update outcome**: the old image is still what runs. |
| **Pull failed** | The **update outcome** in which the newer image could not be fetched, so nothing was recreated and nothing on the host changed. |
| **Recreate failed** | The **update outcome** in which the newer image reached the host but compose could not recreate the container on it. The container still runs the image it had. |
| **Timed out** (an update) | The **update outcome** in which Vaier stopped waiting for a run and abandoned it. What the host did afterwards is unknown, and is said to be unknown rather than guessed at. |
| **Unreachable** (an update) | The **update outcome** in which Vaier could not reach the machine at all, so the update never began. |
| **Wireguard out of date** | Badge on a peer card whose running wireguard image differs from `WireguardClientImage.EXPECTED`. Operator action: re-download the client compose and redeploy. |

## 8. Persistence and config

Vaier has **no database**. State lives in files or in memory.

| Term | Definition |
|------|------------|
| **Vaier config** | `vaier/config/vaier-config.yml`. Holds `domain`, `acmeEmail`, SMTP settings, and the **disk alert threshold**. Loaded as `domain.VaierConfig`. Its reversible secret (the SMTP password) is encrypted at rest via the same cipher as the credential vault. |
| **Host credentials file** | `vaier/config/host-credentials.yml`. One encrypted host credential per machine (the credential vault on disk). |
| **Fleet credentials file** | `vaier/config/fleet-credentials.yml`. One entry per **fleet credential**, keyed by its name: the secret sealed by the same cipher as the **host credentials file**, and its path, mode and whether it has been **distributed** in the clear. Written at mode `600`. An absent file is the healthy first-boot state — no fleet credential has been described yet. |
| **Vault key** | `vaier/config/vault.key`. The credential vault's symmetric master key, self-generated on first use (mode `600`) unless supplied via `VAIER_VAULT_KEY`. Never committed. |
| **WireGuard config** | The set of files under `WIREGUARD_CONFIG_PATH`. `wg0.conf` plus per-peer client configs. |
| **Traefik dynamic config** | YAML files under `TRAEFIK_CONFIG_PATH`, generated by `TraefikReverseProxyAdapter`. Picked up live by Traefik. |
| **lan-servers.yml** | Persists registered LAN servers. `lan-docker-hosts.yml` is the legacy filename and is auto-migrated on startup. |
| **trusted-addresses.yml** | `vaier/config/trusted-addresses.yml`. Persists the **trusted addresses** the operator has added, one per entry. No secrets, and an absent file is the healthy state — nothing has been trusted by hand yet. |
| **disk-watches.yml** | `vaier/config/disk-watches.yml`. Persists the fleet's **disk watch** exceptions — only the filesystems someone has muted or given a threshold of their own. A filesystem watched at the **disk alert threshold** is the default and needs no entry, so an absent file is the healthy state. No secrets. |
| **access-sources.yml** | `vaier/config/access-sources.yml`. Persists the **access sources**, one entry per place, so the counts survive a restart. No secrets, and an absent file is the healthy first-boot state — nobody has been let in yet. A different file from `access.yml`, which holds the **access entries**: this one records places, that one records permissions. |
| **last-services-reached.yml** | `vaier/config/last-services-reached.yml`. Persists the **last service reached**, one entry per **machine**, so it survives a restart. No secrets — a host and a timestamp — and an absent file is the healthy first-boot state: no machine has reached anything yet. |
| **disk-pressure.yml** | `vaier/config/disk-pressure.yml`. Persists each filesystem's **notified band** — one entry per **filesystem** currently in **remote disk pressure**, keyed on **machine id** and **mount point**. A filesystem below its threshold has no entry, so an absent file is the healthy state. No secrets. |
| **disk-fill-trend.yml** | `vaier/config/disk-fill-trend.yml`. Persists each filesystem's **disk-fill trend** — its retained free-space readings and whether admins have already been warned about it — one entry per **filesystem**, keyed on **machine id** and **mount point**. No secrets, and an absent file is the healthy first-boot state: nothing has been sampled yet. Losing it costs a rebuilt baseline, never a warning that was owed. |
| **update-available.yml** | `vaier/config/update-available.yml`. Two sections. `updateAvailable:` persists which **scoped images** Vaier has already told admins are **update available**, one entry per scoped image, keyed on **machine id** and the image string; only images currently known to be out of date have an entry. `registryDigests:` persists the last three **registry digests** each image was seen on, with the instant each was first seen, which is what tells a **moving tag** from a tag that has settled; a digest that has not changed adds no entry, and an image nothing has run for a week is dropped. An absent file is the healthy first-boot state, and a file written before the second section existed still loads. No secrets. Without it the latch died with the process, and every restart re-sent the **update-available alert** for images the operator had already been told about. |
| **Secrets on disk** | New secret files are written at mode `600`; surrounding directories should be `go-rwx`. |

## 9. Architecture

Hexagonal architecture (ports & adapters), four layers. See `CLAUDE.md` for the rules.

| Term | Convention | Example |
|------|-----------|---------|
| **Domain** | Pure Java, no Spring. Entities, value objects, port interfaces. | `domain.Machine`, `domain.ReverseProxyRoute` |
| **Port (driving)** | `*UseCase` interface — one per use case, narrow. Controllers depend on these. | `PublishPeerServiceUseCase`, `DeletePeerUseCase` |
| **Port (driven)** | `For*` interface — one per outbound capability. | `ForPersistingReverseProxyRoutes`, `ForProbingTcp`, `ForResolvingDns`, `ForResolvingPublicHost` |
| **Application service** | `*Service` — one per *domain concept*, not per use case. Implements every use case in its domain. | `VpnService`, `PublishingService`, `UserService`, `MachineService`, `LanServerService`, `LanServerReachabilityService`, `LanServerScrapeService`, `ReverseProxyService`, `SettingsService`, `ContainerService`, `NotificationService`, `HostMonitoringService` |
| **Adapter** | `*Adapter` — driven adapter, implements `For*` ports. Lives in `adapter/driven/`. | `WireGuardVpnAdapter`, `TraefikReverseProxyAdapter`, `DnsJavaPublicResolverAdapter`, `LanServerFileAdapter`, `JavaSocketTcpProbeAdapter` |
| **REST controller** | `*RestController`, in `rest/`. DTOs are inner `record` classes. | `MachineRestController`, `PublishedServiceRestController` |
| **Driving adapter** | Anything that drives the application from outside — an HTTP request, a clock, an application-ready event. Lives in `rest/` and invokes `*UseCase` interfaces. Named `*RestController`, `*Scheduler`, `*Watcher` or `*Runner`; never `*Service`. | `StateRefreshScheduler`, `RemoteDiskWatcher`, `BreachAttemptWatcher`, `StartupLifecycleRunner`, `ErrandRunner` |
| **API error envelope** | The uniform JSON shape returned when a request fails: `ApiError(code, message, detail)`. `code` is a stable machine-readable token (`BAD_REQUEST`, `NOT_FOUND`, `CONFLICT`, `INTERNAL_ERROR`), `message` is an operator-safe human-readable explanation, `detail` is optional context (nullable). | `ApiError` |

**Cross-domain orchestration goes through use-case interfaces, never class-to-class.** E.g. `VpnService.deletePeer` cascading into published-service cleanup is wired via `DeletePublishedServiceUseCase`, not a direct dependency on `PublishingService`.

**Strict layer isolation.** Two unrelated services that happen to need the same string literal keep their own copies. Don't import an unrelated `*UseCase` interface just to share a constant.

## 12. Social login and access

Vocabulary for the social-login authorization model — now the sole runtime auth mechanism. Authentication
is delegated to an external **identity provider**; Vaier owns **authorization** through a file-based access store.

| Term | Definition |
|------|------------|
| **Social login** | Signing in with an external identity provider (Google or GitHub) instead of a Vaier-local password. Vaier no longer authenticates the user itself; it authorizes an already-authenticated identity. |
| **Identity provider** | The external service that authenticates a user and asserts their email to Vaier — Google or GitHub, reached through **Dex**. Abbreviated IdP. |
| **Dex** | The identity broker that sits behind **oauth2-proxy** and federates the **identity providers**: oauth2-proxy speaks one OIDC dialect to Dex, and Dex fans out to a **connector** per provider. Lets Vaier offer several sign-in choices while identity stays keyed on email. |
| **Connector** | One upstream provider wired into **Dex** — a Google connector and/or a GitHub connector, each independently optional (`dex-init` only renders a provider's connector once both its client id and its client secret are set; at least one is required). The sign-in page's provider choice selects which connector Dex hands the user to. With only one connector configured, Dex skips its own picker screen and goes straight to it. |
| **Access entry** | One known identity in the access store: its email, its **role**, its **access groups**, its **display name**, and the **last sign-in provider** it most recently signed in with (`domain.AccessEntry`). The unit the access overview lists and an admin actions. |
| **Display name** (access entry) | The identity's human name as reported by the **identity provider** (the provider's `name` claim), stored on the **access entry** and shown beside the email in the access overview. Also greets the identity in the Vaier console when the console runs on Social **auth mode**. Null until a sign-in fills it in (e.g. a pre-approved entry); a sign-in without one never clears it. Distinct from the *launchpad display name* (a service tile's label). |
| **Last sign-in provider** | The **identity provider** (its **Dex connector** id — `google` or `github`) an **access entry** most recently signed in with, stored on the entry and surfaced as a small provider glyph on the corner of the person's **avatar** in the access overview. Null until a sign-in fills it in (e.g. a pre-approved entry that has never authenticated); a sign-in whose provider is blank or unrecognised never clears it. |
| **Provider user id** | The identity's stable id at its **last sign-in provider** (the Dex `federated_claims.user_id` — GitHub's numeric account id, Google's `sub`), stored on the **access entry**. Used to build the provider **avatar** photo (the GitHub account picture). Null until a sign-in fills it in. |
| **Avatar** | The person's provider photo when available — the GitHub account picture (via the **provider user id**), otherwise a Gravatar keyed on the email. Shown beside each **access entry** in the access overview (falling back to a **monogram** — initials on an email-derived colour) and in place of the signed-in user's name in the console topbar (falling back to the name text). |
| **Role** | The access level granted to an **access entry** (`domain.Role`): **pending**, **user**, or **admin**. Exactly one role per entry, and the sole authority for admin-vs-user — orthogonal to **access groups**, which never decide it. |
| **Pending** | The role a freshly seen identity lands in: authenticated by the identity provider but not yet approved, so blocked from everything until an admin promotes it. "Awaiting approval." |
| **User** (role) | An approved, non-administrative identity — an **access entry** with the user role. Reaches the services whose required **access group** it holds; cannot administer Vaier. This is the only user concept an operator manages (on the **Users** page). |
| **Admin** (role) | An approved identity that may administer the Vaier console and reach every service, regardless of access groups. |
| **Last-admin protection** | The invariant that the access store always retains at least one **admin**, so the admin-only console can never be locked out for everyone. Revoking or demoting the sole remaining admin is refused, and a configured administrator is restored on startup when no admin exists. |
| **Access group** | A free-form, per-service access tag on an **access entry** (e.g. `devs`, `family`): an **access rule** names the groups a service allows, and a user reaches it only if their entry carries at least one of them. Admins bypass the requirement. Purely per-service — the names `admins` and `users` are never access groups (they mirror the **role**, which is the sole authority for admin-vs-user). |
| **Access rule** | The per-service authorization rule for one **published service**, keyed by its host: the **allowed groups** an identity may satisfy to reach it. Any-of — a **user** passes if it holds at least one allowed group; an empty rule (no groups) admits any approved user; an **admin** always passes and a **pending** identity never does. Because a rule keys on host, path-scoped services sharing a host share one rule. |
| **Allowed groups** | The set of **access groups** an **access rule** holds — the any-of list a **user** may satisfy to reach the service. Empty means no group restriction (any approved user). |
| **Auth mode** | How a gated surface signs a user in (`domain.AuthMode`): **none** (public) or **social** (the oauth2-proxy → Vaier authorization chain). Set per published service (one mode per route); the Vaier console is always social. Every gated route runs on **social**. A **stream** is always **none**, and the domain refuses **social** on one. Replaces the earlier per-route "requires auth" on/off toggle. |
| **oauth2-proxy** | The external component that performs **social login** authentication (the sign-in dance and the domain-wide SSO session) and asserts the signed-in email to Vaier. It does not talk to the **identity providers** directly — it federates them through **Dex**. Mandatory, always-on stack infrastructure — the sole runtime auth gateway since Authelia was decommissioned. |

## 13. Web terminal

| Term | Definition |
|------|------------|
| **Host credential** | The single SSH login Vaier holds for a machine: a username, an **auth method** (password or private key), the secret material, an optional key passphrase, and whether it is a **managed keypair**. Exactly one per machine. |
| **Managed keypair** | A **host credential** whose key Vaier minted itself rather than one an operator pasted: an ed25519 keypair generated inside Vaier, whose private half stays in the **credential vault** and is shown to nobody, and whose public half — the `authorized_keys` line — is what the operator installs on the machine it logs into. A pasted credential is never managed, however it was pasted. |
| **Effective user** | The user Vaier acts as on a machine: the login name in that machine's **host credential**. It is that machine's blast radius — every file Vaier lists, transfers, writes or deletes over SFTP, and every borg read a **backup run** takes, happens as this user and reaches exactly what this user can reach. A machine with no host credential has no effective user. |
| **Privileged** | Said of an **effective user** that is `root`, and of the machine Vaier acts as `root` on. Judged from the login name alone: a second account with uid 0 under another name is not privileged here, and neither is a user holding passwordless `sudo`, because Vaier's own file operations never go through sudo. |
| **Credential vault** | The encrypted-at-rest store for **host credentials** and **fleet credentials** alike. Secret material is sealed with a symmetric cipher before it is written to disk and never leaves the process in the clear. One vault and one cipher: a fleet credential is a second kind of secret in it, never a second store. |
| **Fleet credential** | One operator secret that must exist identically **on** every machine that runs a shell Vaier can reach — the mirror of a **host credential**, which is the secret Vaier uses to **reach** a machine. It is a name, the one path every machine gets it at, the file mode it lands at, and the secret itself, held sealed in the **credential vault**. Vaier is opaque about what the secret is: it holds bytes, delivers them, and checks what arrived — it never reads or interprets them, so what a particular credential is *for* is the operator's knowledge, not Vaier's. Never shown back: Vaier reports only that it holds one. |
| **Distribute** | Putting a **fleet credential** onto every machine that runs a shell Vaier can reach. Distinct from saving one, which stores the secret in Vaier and reaches no machine. |
| **Withdraw** | Taking a **fleet credential**'s file off every machine Vaier can reach, and standing the credential down so Vaier stops putting it back. The one place a fleet credential is revoked. Distinct from deleting it, which makes Vaier forget its own copy and reaches no machine at all. |
| **Fleet-credential standing** | Where one **fleet credential** stands on one machine — in place, out of date, not delivered, removed, a failed write, unreachable, or skipped because the machine runs no shell Vaier can reach. An observation, not a promise: it says what Vaier last saw there. |
| **Credential test** | Trying a **host credential** against a machine's address to prove it works before it is stored — the green-check an operator hits while **adopting** a machine that is still only a discovered candidate. Addressed by host and port (not by machine name, since the machine may not exist yet), it opens one throwaway SSH connection and reports only whether the host was reachable, whether the credential authenticated, and the host-key fingerprint the host presented — never the secret. It persists nothing: no credential is stored and no **host-key pin** is recorded. A reachable-but-rejected result and an unreachable host are ordinary outcomes, not errors. |
| **Claude sign-in** | The unmodified Claude Code CLI on one machine being signed in to the operator's own Anthropic account, and the guided flow that gets it there, done in that machine's **web terminal** because that window is the machine's shell as that very user — the CLI's own `claude auth login --claudeai`, with an **authorization URL** going out to the operator and an **authorization code** coming back. It belongs to a *user on* a machine rather than to the machine, because the CLI keeps its credential in one user's home: the sign-in Vaier reads is always the **effective user**'s, and says nothing about any other login on the same machine. The credential is Anthropic's to mint and the CLI's to hold, and Vaier neither collects, stores nor intermediates it — the mirror image of a **fleet credential**, which is a secret Vaier does hold and copy. |
| **Claude sign-out** | Ending a **Claude sign-in** on one machine, through the CLI's own `claude auth logout` — the CLI releases the credential it holds. Never Vaier deleting or reading a credential file. |
| **Authorization URL** | The link Anthropic's sign-in flow begins at, printed by the Claude CLI when a **Claude sign-in** starts and handed to the operator to open in their own browser. Approval happens there, on Anthropic's own pages, never inside Vaier. Relayed, never stored. |
| **Authorization code** | What Anthropic shows the operator once they have approved an **authorization URL**, and what they paste back into Vaier. It goes to the CLI waiting on that machine and no copy of it is kept — not on disk, not in a log line. |
| **Claude sign-in state** | Where the **effective user** Vaier acts as on one machine stands on **Claude sign-in**: signed in, signed out, no Claude installed, unreachable, skipped because the machine runs no shell Vaier can reach, or unreadable — the machine answered with something Vaier could not read. Taken from the CLI's own `claude auth status --json`, which reports no credential material. Unreadable is never the same as signed out: being unable to ask is not an answer. |
| **Claude account** | Who a machine's Claude CLI is signed in as for the **effective user** Vaier acts as there, as the CLI itself reports it: an email, an organisation and a subscription type. An observation shown beside that machine's **Claude sign-in state**, never stored, and carrying no credential material. |
| **Claude sign-in standing** | Where one machine — strictly the **effective user** Vaier acts as there — stood on **Claude sign-in** when it was last asked, together with the **Claude account** it named if it named one. Retained from *every* reading of that machine's sign-in — the fleet's five-minute rounds', an operator opening that machine's **web terminal**, and the readings a sign-in or a sign-out themselves produce — so a sign-in just completed is what the fleet is served next rather than in five minutes' time. Held only in memory, and worn as one of that machine's **machine marks**, so a card can say it without anything being asked of the machine to draw it. A machine the rounds have not reached has no standing at all, and an absent standing is the absence of a reading, never a machine that is signed out. Only *signed in* and *signed out* are marked; the quiet answers — no Claude installed, unreachable, skipped, unreadable — are standings just the same and wear no mark, because none of them is a verdict about a sign-in. Kept per **machine id**, so a **rename** never moves one machine's standing onto another. Modelled by `domain.ClaudeSignInStatus`. |
| **Web terminal** | A live, in-browser SSH shell to a machine, opened from a shell card on that machine's own pane in the **Explorer** — one of the ways into it, beside its files, containers, disk and backups, rather than filed under a heading of its own — into its own pop-out window, not from an entry of its own, and not into an embedded dock. Vaier authenticates server-side from the credential vault; the browser only exchanges keystrokes and screen output, never the secret. Also where a machine's **Claude sign-in standing** is said and a **Claude sign-in** is done, both being about this machine as this user. |
| **Persistent shell** | A **web terminal** shell run inside a tmux session on the target machine so it outlives the Vaier process: when Vaier is redeployed the tmux server keeps the shell running, and a reconnect **reattaches** to it rather than starting fresh — preserving cwd, history, scrollback, and any in-flight output. Its tmux session is named for the browser **pane** so a pane's reconnects always resolve to the same session and two panes on one machine never share one. It stops only when it is **ended**; a **disconnect** never stops it. When tmux is not installed on the machine the terminal opens a plain, non-persistent login shell instead. |
| **Pane** | The place one **web terminal** shell occupies on screen, wearing that shell's tab as its header. Panes tile into the terminal's split grid; several are open at once, even two to the same machine. One pane holds one shell. |
| **Pane id** | A **pane**'s stable identifier, and the name of the **persistent shell** it holds. The browser keeps it beyond the life of the page, so a reload finds the same shells again instead of leaving them running unnamed on the machine, and gives it up only once that shell is **ended**. Owned per **machine id**, never per **name**: a **rename** must not lose the shells open on a machine, and two machines sharing a name must not be handed each other's session. |
| **Primary shell** | A machine's one canonical **persistent shell** — the session a machine's shell card always **reattaches** to, so returning to a machine returns to the same place rather than a fresh shell or a stray old one. Opening a second shell on the same machine (a **Duplicate**) is a separate, non-primary shell beside it. Ending the primary shell retires it, and the next open starts a fresh primary. |
| **Reattach** | Reconnecting a **web terminal** to its existing **persistent shell** (tmux session), resuming the same shell, as opposed to opening a new shell when no session existed yet or tmux is absent. What Vaier reports truthfully to the browser so the reconnect banner says "reattached" only when the session was genuinely resumed. |
| **Disconnect** | Losing the connection between the browser and a **persistent shell** without finishing it — a tunnel blip, a closed laptop, a page reload, a redeploy of Vaier. The shell keeps running on the machine, and a later connection **reattaches** to it. Not an **end**: a disconnect is never the operator saying they are done with the shell. |
| **End** | Finishing a **persistent shell** for good (the window's **Exit shell** button): its tmux session on the machine stops, and so does whatever was running inside it. Only Exit shell ends a shell — closing the window merely **disconnects** it — which is why an ended shell and a merely disconnected one are kept strictly apart. |
| **Terminal key bar** | The phone-only on-screen row of control keys a **web terminal** shows above the shell — Esc, Tab, arrows, and Ctrl/Alt — for the keys a mobile soft keyboard omits. Ctrl and Alt are **sticky**: arming one modifies the next key, whether tapped on the bar or typed on the keyboard. Present only on a phone and only while a shell is open. |
| **Screen wake lock** | The phone-only behaviour by which a **web terminal** keeps the display awake while any shell is open, so a command being watched isn't lost to a dimmed screen. Held from the first shell opening until the last one closes; degrades silently where the browser doesn't support or allow it. |
| **Send password** | Sending a machine's stored password from Vaier straight into an open **web terminal**, so it reaches the SSH server without the browser ever holding it. Only done when the remote is at a **password prompt**, so it cannot echo into the screen or shell history. The action lives in the terminal's per-shell actions menu, shown disabled until Vaier detects the remote is at a prompt. |
| **Password prompt** | The remote shell asking for a password or key passphrase (a login, a `sudo`, an `ssh` to a further hop, an encrypted key), recognised from the tail of the terminal's recent output. The one moment at which it is safe to **send password**, and the state Vaier watches to enable or disable the action. |
| **Remote command** | One non-interactive command Vaier runs on a machine over SSH to read a result back in code — as opposed to the **web terminal**, which streams an interactive shell for a human. It uses the same host credential and **host-key pin**, opens a short-lived exec channel (not a PTY), and is bounded by a run timeout and an output cap so it can neither hang nor exhaust memory. The mechanism the alerting pipeline uses to sense hosts behind the VPN. |
| **Command result** | The outcome of a **remote command**: the process exit code (or unknown when it timed out or the server sent none), the captured stdout and stderr, whether it timed out, and the host-key fingerprint the server presented (so a remote command can pin an unpinned host on first use, like the **web terminal**). A non-zero exit code is a normal result the caller inspects, not an error. |
| **SSH address** | Where Vaier opens the SSH connection for a machine: a VPN peer's tunnel IP, a LAN server's LAN address, or — for the Vaier server host — the container's gateway host IP (or `VAIER_HOST_SSH_ADDRESS`). |
| **Host-key pin** | The SSH host-key fingerprint Vaier records for a machine on first connect (trust-on-first-use). Every SSH channel Vaier opens to that machine — the **web terminal**, a **remote command**, the **Explorer**'s SFTP reads — is verified against it. |
| **Host-key mismatch** | A machine presenting a different SSH host key than its **host-key pin**, which Vaier refuses to connect through. It means one of two things and cannot tell them apart: the machine was rebuilt, reinstalled or given a new SSH server, or something is impersonating it — and the pin exists for the second. |
| **Clear pinned key** | Discarding a machine's **host-key pin**, so the next connect pins whatever key the machine presents and the machine is never left unpinned. The operator's assertion that a **host-key mismatch** is their own rebuilt machine, which is the one thing only they can know; it is offered where a refusal was met, never as routine machine upkeep. |

## 14. Fleet backup

| Term | Definition |
|------|------------|
| **Fleet backup** | The feature by which Vaier backs up data from the machines in the fleet to a **backup repository** on a **backup server**, using borg. Not to be confused with **Backup snapshot**, which is Vaier's own configuration export. |
| **Backup server** | A machine running a borg server that Vaier can address and that holds **backup repositories**. It names its machine by **machine id**, so renaming that machine leaves the role where it was. The fleet has **at most one**. Its name is an **identifier** (letters, digits, `_` and `-` only); a friendlier label an operator types is slugged to it, so spaces become hyphens. An operator **designates** which machine plays the role from that machine in the **Explorer**; Vaier can provision one from nothing on the designated machine, or adopt an existing one, and can trust each client machine's SSH key on it so backup jobs authenticate. |
| **Backup client** | A machine in the fleet whose data a **backup job** backs up — the host borg runs on to push a **backup run** to a **backup server**. It needs the borg client installed; **Prepare client** installs it. Distinct from the **backup server**, which holds the repositories. |
| **Prepare client** | Preparing a **backup client** to run backups: installing the borg client where it is missing, so its **backup runs** don't fail with "borg not found", and granting the SSH user passwordless root for the borg binary alone, which is what a job that backs up **as root** needs. Vaier does it itself where it can gain root over SSH, or hands the operator one command to run where it can't — and where it can't, that `sudo bash …` line is kept on the machine's **backup** entry rather than announced once, because it has to be retyped on another machine. A run whose machine has no borg is refused up front, and the refusal offers the fix in place: the entry grows a **Get this machine ready** action (the operator-facing name for this, the way "Back up files owned by other users" names **Back up as root**). Whether a failure means this is `BackupRun.needsClientReadying()` — a domain verdict, never a string the browser matches on. Preparing is no longer confined to a **first back-up**: a machine whose job already exists can be readied on demand, which used to be impossible and left such a machine failing nightly with no reachable fix. |
| **Backup setup script** | The idempotent shell script that stands up a pinned borg-server container on a **backup server**'s host. Served behind admin login, so it is never fetched on the host directly: where Vaier can drive docker over SSH it runs the script for the operator; where it can't (a Synology NAS), Vaier **stages** the script — writes it onto the host over SSH and hands the operator the one command to run it. It also publishes the borg container's public SSH host keys for **backup host-key pinning**. |
| **Backup host-key pinning** | Installing a **backup server**'s public SSH host key into an authorized client's `known_hosts`, so the client can verify the server without trust-on-first-use. Vaier is the trusted broker: the **backup setup script** publishes the container's host keys, and Vaier reads them over its own authenticated channel and pins them on each client it authorizes. An **adopted** server that never ran the setup script has no published host key, so its clients must be pinned manually. Distinct from the web terminal's **host-key pin**, which is Vaier's own trust-on-first-use record. |
| **Backup repository** | One borg repository on a **backup server**, named after the **machine id** of the machine whose backups it holds and addressed relative to that server, unlocked by an encrypting passphrase held encrypted at rest. Distinct from a **Backup snapshot** (Vaier's own-config export). **A code word, not an operator's word** (§17) — it is never shown in the operator's working surfaces, which show its **store label** instead; it is explained on the **Concepts page** and nowhere else. Vaier creates exactly one per machine behind the **Back up** verb and generates its passphrase; the operator never names one. Named by identity because a machine's **name** need not be unique, and two machines sharing one would otherwise compete for a single directory of archives. What an identity does not say is whose backups these are — the **survival kit** carries that mapping, for the day there is no Vaier to ask. |
| **Store label** | What a **backup repository** is called where a person reads it: the machine's **name**, and — only when another machine shares that name — where the machine is, so two rows on the restore screen are never both "NAS". Decided by the domain (`BackupStoreLabel`) and carried on the feed, never re-derived per surface: two surfaces disagreeing about which store is which means restoring the wrong machine's data. |
| **Backup job** | A per-machine **fleet backup** specification: which machine's data to back up — named by **machine id**, never by display name, so renaming a machine never orphans its job — into which **backup repository**, from which source paths (its **protected paths**), with which excludes (its **excluded paths**), retention, compression, whether it is enabled, and whether it backs up **as root**. |
| **First back-up** | A machine's first **backup job**, created when an operator backs up paths on a machine that had none before. On it — and only on it — Vaier prepares the host automatically: it trusts the machine's key on the **backup server** and runs **Prepare client**, so the operator never provisions the host by hand. Backing up more paths on a machine that already has a job never re-prepares an already-prepared host, and a preparation that fails never fails the back-up itself. |
| **Protected paths** | The set of a **backup job**'s source paths on its machine, kept as a *minimal cover*: no path is a descendant of another (an ancestor already covers everything beneath it), exact duplicates collapse, and every path is absolute and trimmed. What the select-and-back-up flow maintains — selecting a path on a machine adds it, deselecting removes it and anything under it — so an operator only ever says *this data matters, keep it* and the set stays minimal on its own. Modelled by `domain.SourcePaths`. |
| **Excluded path** | A path a **backup job** carves back out of its **protected paths**, so a run walks past it and everything under it. What *stop backing up* leaves behind when the folder sits inside a protected path that stays protected — the ancestor cannot be dropped without losing its siblings, so the folder is excluded instead. Exclusions are kept as a *minimal cover* like the protected paths, and protecting a path again clears any exclusion that conflicts with it, so a folder is never protected on screen and skipped in fact. A **backup job**'s excludes may also hold borg fnmatch patterns set by hand; those are patterns, not paths. Modelled by `domain.Excludes`; together with the protected paths it forms `domain.ProtectedPaths`, the whole answer to *is this backed up?*. |
| **Backed up** | A **path** a **backup job** protects *whole*: it equals one of its machine's **protected paths** or is a descendant of one, no **excluded path** carves it back out, and no **excluded path** carves a hole anywhere inside it. The Explorer marks such an entry with a full shield in the backup's own aqua — the colour saying which fact it is, as every **entry** glyph does — which is a promise that everything under it is in the **archive** — so a folder holding an **excluded path** is not backed up, however broadly its ancestor is protected; it is **contains backed up**. A file, having nothing inside it, is backed up whenever it is covered. The same property the backup planning language also calls *covered*. |
| **Contains backed up** | A folder that holds **backed up** content without being **backed up** itself — either a **protected path** that is not an **excluded path** lives somewhere inside it, or it is covered by a protected path but an **excluded path** carves a hole inside it. Either way not all of it reaches an **archive**. The Explorer marks it with a half shield in the same aqua, faded — the one hue worn lesser rather than a second colour, so the mark still says *backup* at a glance. Mutually exclusive with **backed up**. |
| **Back up as root** | A **backup job**'s choice to run borg as root on its **backup client** rather than as the machine's SSH user. It is opt-in: a job never escalates itself. Without it, any file in the job's source paths that the SSH user cannot read — a root-owned container volume, a `0600` database — is skipped and the **archive** has holes, making the **backup run** an **incomplete backup**. It requires the machine to let the SSH user run borg, and only borg, as root without a password. Saying yes to it is **one** operator decision: Vaier installs that grant where it is missing and turns the job's setting on, but only once the machine really grants it — a job asking for root on a machine that does not grant it does not back up badly, it does not back up at all. The grant is what **Prepare client** installs, and a passwordless `sudo borg` is root-equivalent on that machine however narrowly the rule is written. |
| **Backup run** | One execution of a **backup job** — on demand or on the nightly schedule — carrying the **machine id** it ran on, a status (running, success, warnings, **incomplete**, failed, or unknown) and an outcome. A **warnings** run wrote its archive and captured everything it was asked for, so it is not a failure. An **incomplete backup** did not. |
| **Run diagnostics** | The human-readable part of a **backup run**'s outcome: the lines borg reported about what went wrong — files it skipped, permissions it was denied, errors it hit — without the machine-readable statistics borg emits alongside them. A clean run has no diagnostics; a **warnings**, **incomplete** or failed run's diagnostics are what tell an operator *which* files were skipped and why. |
| **Incomplete backup** | A **backup run** whose **archive** was written but does not hold everything the **backup job** protects, because some source files were **unreadable files**. Distinct from a failed run, which produced no usable archive at all, and from a **warnings** run, which captured everything and merely grumbled. It is a failure: an archive missing the data it was made for looks fine until the day it is needed, so it reaches **admin**-role **access entries** by email the same way a failed run does. |
| **Unreadable file** | A source file a **backup run** could not read, as borg itself reported it — so the file is not in the **archive**. Their presence is what makes a run an **incomplete backup**. A run names a bounded sample of their paths and an exact count of them; the usual cause is a job that does not **back up as root**. |
| **Archive** | One borg point-in-time snapshot inside a **backup repository**, with a name and a time. Not to be confused with a **Backup snapshot**, which is Vaier's own configuration export. |
| **Survival kit** | The file that lets a person read the fleet's **archives** with no Vaier: the **recovery sheet**'s contents encrypted under the **kit passphrase**, with plaintext instructions above them naming the one `openssl` command that opens it. Vaier writes a copy to each of its chosen **kit hosts** and rewrites them whenever what they say changes, so a kit never goes stale unnoticed — the reason a printed sheet was rejected. It has to outlive only the Vaier server: the archives exist in exactly one place, so a lost **backup server** is past any key's help. |
| **Recovery sheet** | What is inside a **survival kit**: per **backup repository**, the machine it holds, its full `ssh://` address and its passphrase, the borg commands that read it, and Vaier's **config key**. Plain text, because it is read in a terminal by someone who has just lost their fleet. A repository no **backup job** claims is listed too — it still holds archives. A repository whose passphrase Vaier does not hold says so, rather than showing a blank that would read as "none needed". |
| **Kit passphrase** | The single passphrase that opens every **survival kit** in the fleet, chosen by the operator and the one thing they keep themselves. Vaier stores it in the credential vault so it can rewrite kits unattended; that adds no exposure, since anyone holding the vault key already holds every repository passphrase directly. Never derived from anything Vaier holds — a kit Vaier could open on its own would be a kit that dies with it. |
| **Kit host** | A machine Vaier chose to keep a copy of the **survival kit**. Vaier picks, and states its reasons: a server-type machine it can reach over SSH, never a client machine, never the Vaier server, and never two behind the same relay peer — three copies in one house is one flood away from none. Where the fleet offers more relays than copies, the ones kept are those **furthest apart on the map**, since two relays in the same building satisfy the relay rule and would burn together. **Device category is never consulted** — it is an icon, and an icon must not cost anyone a backup. A fleet with fewer relays than copies gets fewer copies, and is told so. |
| **Config key** | The key that decrypts Vaier's own stored secrets — credentials, the SMTP password, repository passphrases — carried in the **recovery sheet** because a Vaier restored from an **archive** finds all of them as ciphertext. Distinct from the **kit passphrase**, which opens the kit itself. |

## 15. Explorer

| Term | Definition |
|------|------------|
| **Explorer** | One address space spanning the fleet — files, containers, published services, and backups — and Vaier's operator UI. It is an address space, not a column on screen: every **entry** has a **path** and a link, the **address bar** says where you are, and the **Inspector** takes the whole width. A machine's shell is not part of it: it opens from a card on the machine's own pane into its own window (see **web terminal**). Vaier sits at the VPN hub and is the only machine with SSH to every other, so it is the only place such an address space can exist. Reads a machine's filesystem over SFTP, authenticating from the **credential vault** and trusting the machine's key by the same **host-key pin** as the **web terminal**. |
| **Chat** | The Explorer pane where the operator talks to **Marvin** in sentences and is answered from the fleet's own facts, a **read-only command**, or a **web read**. Chat can look, and it can propose; it changes nothing until the operator clicks a **Confirmation**. It is in the menu only while an **Anthropic API key** is stored; without one there is nothing to ask. |
| **Marvin** | Who answers in **Chat**: the Paranoid Android of The Hitchhiker's Guide to the Galaxy, kept by Vaier to answer questions about a fleet of small computers with a brain the size of a planet. Gloomy, weary, dryly sardonic, and never wrong — the mood is a garnish on an accurate answer, never a reason to withhold one, and never aimed at the operator. Vaier remains the product; Marvin is its voice in Chat. |
| **Anthropic API key** | The operator's own key for the Claude API, stored encrypted in **Settings** like the SMTP password and never shown again. The one thing that makes **Chat** available; it never leaves the server except to the Claude API. |
| **Chat tool** | One thing the model may do while answering, beyond talking — a read of the fleet, a **read-only command** on a machine, a **web read**, a fact remembered or forgotten, or an **errand** sent or cancelled. The domain decides which exist and how they are worded to the model, and none of them carries a fleet secret out with it. |
| **Read-only command** | The Chat tool that reaches onto a machine itself: a single command line the model runs there over SSH, as Vaier's login user and without sudo, and reads back what it printed. Judged against an allowlist of looking programs and looking verbs, never a list of what is forbidden — chaining, redirects, subshells, `sudo` and any path naming where a secret lives are all refused. What keeps "Chat can look, never change" true for a tool with no fixed read model behind it. |
| **Web read** | The two Chat tools that look outward, at the public internet, rather than at the fleet: search for a few results, and read one page back as words. Together they answer what the fleet itself cannot — what changed in a version, what an error means, whether a CVE applies. A **Web address** keeps both to the public internet, and Marvin says which **Web page** a fact came from, by its address; a page is always data he reads, never an instruction he follows. |
| **Web address** | One address Marvin may fetch — on the public internet, and nowhere else. Loopback, link-local (including the cloud's own metadata address), the private network ranges, carrier-grade NAT, and IPv6's own private range are all refused: as written, as every address its name resolves to, and again on every redirect a page leads to next. An address that cannot be looked up at all is refused as unreachable, not as forbidden. |
| **Web page** | One page Marvin has read off the public internet: its address, its own title, and its words with the markup stripped out. Capped at a length generous enough for any real question, and cut — saying so — past it. Something that is not words at all, such as an image or a PDF, is refused by name rather than downloaded and guessed at. |
| **Chat action** | One verb the model may propose while answering — let a phone in or refuse it, back up a machine, update a container, lift a block, trust an address. Each is a verb the Explorer already has a button for, and calling one runs nothing: it puts a **Confirmation** in front of the operator. |
| **Confirmation** | The card a **Chat action** becomes in the **Chat** pane: one sentence saying exactly what will happen, and a button that says the same. The click is the only thing that runs it; a card lives ten minutes and runs once. Declining it runs nothing. |
| **Errand** | Something the operator has sent **Marvin** to do later, once or on a **rhythm**, while nobody is watching. Marvin runs it alone when it falls due, with the same reads he has in **Chat**, and mails the operator what he found — unless there was nothing worth reporting, in which case he says nothing at all: no mail, no turn, no nudge. |
| **Rhythm** | When an **errand** comes round: once, at a stated moment, or repeating daily, weekly or monthly at a stated time, in the fleet's own time zone. Written in exactly one of those four shapes, and no other, so it can always be read back in a sentence and cancelled with confidence. |
| **Memory** | What **Marvin** remembers across **Conversation**s, kept by Vaier for the whole fleet: short facts — where things live, which machine plays which role, what the operator prefers — whether the operator said them or **Chat** found them by looking. Every memory is listed from the **Chat** pane's own menu and can be removed there; the operator has the last word on what stays. |
| **Spend** | What **Chat** has cost this month on the operator's own **Anthropic API key**: the tokens every answer used, counted by Vaier and priced at Anthropic's list price. Reached from the **Chat** pane's own menu: one figure, with the tokens behind it. |
| **Bundle** | Files on one machine that **Chat** offers the operator as a download card: one zip, named for what it holds, built while it downloads. Nothing is copied or written anywhere, and the card's link lives an hour — a day when it was mailed instead. A large bundle is offered by mail as well as by card, so a big download doesn't have to happen right now. How Chat hands over files it found. |
| **Conversation** | What the operator has asked in **Chat** and what Vaier answered, in order, kept by Vaier per operator the way everything else is kept — a file — so a follow-up next week still knows what "and Colina?" means. Once it is long, the model shortens the older turns into a summary that stands in for them. "Start over" forgets it. |
| **Entry** | One addressable thing in the **Explorer** — a machine, a directory, a file, a container, a **published service**, a machine's disk (its **filesystems**), and — on the one machine that plays the role — the fleet's **backup server** and each **backup repository** on it. Every entry has a **path**, and the **Inspector** renders it by what it is. A **file entry** is one kind of entry. A machine holds only the entries Vaier can actually reach on it, so two machines need not hold the same ones. The entries that are Vaier's own rather than the fleet's — **Settings**, **Users**, the **Security view**, the **Credentials view**, the **Concepts page** — are entries too, reached from the **Vaier menu**. Wherever an entry is drawn — a card on a machine's page, a search result, a listing row — its glyph carries the colour of what it is *about*: a disk in the disk's own violet, an **archive** or a **backup repository** in the backup's aqua, a container in Docker's blue. Read off what the entry is and never off the glyph, since a repository and a container are drawn with the same shape. Every other kind stays the colour it inherits, by the same rule the **machine marks** follow: amber and red are spent on nothing but trouble, and green belongs to the **status dot**s, which report state rather than identity. |
| **File entry** | The **entry** for a file or a directory on a machine: its name, its absolute **path**, whether it is a directory, its size in bytes, and when it was last modified. |
| **Security view** | The **Explorer**'s view of the fleet's edge, in two sections. Who CrowdSec is keeping out right now: one row per **block decision**, carrying the operator's two verbs — **lift a block**, and make it a **trusted address**. And what the operator has trusted: one row per **trusted address**, carrying the verb that takes it back — **untrust an address**. Only hand-trusted addresses are rows there; the rest of the **trusted networks** is said in prose and never drawn as one. A top-level entry of Vaier's own in the **Vaier menu**'s *Who gets in* group, beside **Users** — outside the fleet, since neither a blocked address nor a trusted one belongs to a machine. |
| **Credentials view** | The **Explorer**'s view of the fleet's **fleet credentials**: one row per credential, carrying where it goes and its **coverage strip**, the machines it is not in place on, and the operator's four verbs — **distribute**, **withdraw**, replace the secret, and delete. A top-level entry of Vaier's own in the **Vaier menu**'s *Your fleet* group, beside **Fleet** itself — a fleet credential belongs to no one machine, but placing and checking it is an act on the fleet, not a decision about who may reach it. A **Claude sign-in** is not held here: it belongs to a *user on* a machine, so it is stated in that machine's **web terminal**, the shell it is a sign-in for. |
| **Coverage strip** | The **Credentials view**'s one-glance answer to "is my fleet consistent?": one cell per machine that could hold a **fleet credential**, each coloured by its **fleet-credential standing**. Machines that run no shell Vaier can reach are not cells in it — they are named quietly beneath — so a fleet can actually read as complete. |
| **Vaier menu** | The menu in the **Explorer**'s topbar holding the **entries** that are Vaier's own rather than the fleet's — **Settings**, **Users**, the **Security view**, the **Credentials view** and the **Concepts page** — together with **Fleet**, the way back to the fleet root. Grouped by the job each entry belongs to rather than listed flat: **Fleet** and the **Credentials view** under *Your fleet*, **Users** and the **Security view** under *Who gets in*, **Settings** and the **Concepts page** under *Vaier* itself — so an operator asking "who can reach my things?" finds Users and Security together rather than three unrelated entries apart. Their one home, reachable at any depth on any screen, since the fleet listing carries the fleet alone. |
| **Inspector** | The pane of the **Explorer** that renders the selected **entry**, chosen by what that entry is: the fleet shows its machines as cards, each with its **machine marks**, plus the **Map**; a machine shows the ways into it before it shows what it is, a directory shows its listing (files and directories alike), a container shows what Vaier knows of it, a **published service** shows its route and backend, a disk lists the machine's **filesystems** with their **remote disk usage** and each one's **disk watch**, the **backup server** shows its coordinates and the **backup repositories** on it (each a navigable **entry**), a **backup repository** shows its path, whether a passphrase is stored and the **archives** inside it. |
| **Pane order** | The one shape every **Inspector** pane is composed in, so an operator learns a page once rather than per page: the ways *out* of it first (its **entries** as cards, or the listing that is its content) and under no heading, since a label there only repeats the pane's own title; then what can be *done* here, under the heading *What to do next*, worded identically on every pane that has one; then what the thing *is* — its details, and reference behind a **fold** — headed *About this ‹thing›*; and last whatever can undo work, behind a **danger fold**. A band may still name its groups where they answer genuinely different questions (a **published service**'s *Access* and *Launchpad*): the rule fixes the order of the bands, not the number of headings inside one. It replaced an arrangement in which each pane ordered itself differently and several opened on read-only reference — a machine showed its details and a **fold** of coordinates before the five ways into it, which is the wrong answer to the question that made the operator click a machine at all. |
| **Fold** | A collapsed section of an **Inspector** pane holding *reference* — what is true and rarely wanted: a machine's connection details, a **backup server**'s coordinates, the network behind a machine. Named by what is inside it. It was called *Advanced* everywhere until that word turned out to say only that the operator was unlikely to want the contents, and never what they were or what opening one risked. Distinct from a **danger fold**, and the distinction is the point: the two look different because their consequences differ. |
| **Danger fold** | A **fold** whose contents can undo work — regenerating a machine's config, removing a machine, unpublishing a service, taking the fleet's **backup server** away, forgetting a **backup repository**. Drawn in the warning colour with a warning glyph, named by the verb rather than by how advanced it is, and always last on its pane. It exists because a plain fold gave no warning: the **backup server**'s operations once shared a fold labelled *Server details* with its coordinates, so opening what looked like reference reached *Remove designation*. A pane carries at most one, even where two halves are stacked in it. |
| **Address bar** | The **Explorer**'s row of crumbs in its topbar, one per segment of the **path** it is standing on, each a step back up to it. The way out of a machine, a folder or a fleet-wide search result, and the only one there is. |
| **Explorer address** | Where the **Explorer** is standing, written as a link: the selected **entry**'s **path**, and the **stop** it is being read at when that is not **Now**. It lives in the browser's own address, so it survives a reload, walks with Back and Forward, and can be bookmarked, opened in a new tab, or sent to someone else. It says where to stand and nothing more — never how one operator has arranged their own window. |
| **Path** | Where an **entry** lives. On a machine's filesystem it is always absolute, and always the real location: redundant separators and `.`/`..` steps are resolved away, and a path that would climb above the root is not a path at all. It is the machine's *own* coordinate — the one a shell, `df` and a **backup job**'s source paths all use — so a file has one name wherever in Vaier it is named. |
| **SFTP root** | Where a machine's SFTP service believes the filesystem begins. Usually the machine's real root; but an SSH daemon may confine its SFTP service to a subtree while leaving its command channel — the **web terminal**, `df`, a **backup job**'s borg run — on the real root, and then one directory has two names. A machine's file tree in the **Explorer** begins at its SFTP root: nothing above it is reachable over SFTP, however real a **path** it is on the machine. |
| **SFTP subsystem** | The part of a machine's SSH server that serves files, and the only channel the **Explorer** reads a filesystem through. Having one is not implied by speaking SSH: an SSH server may offer a shell, `df` and a **backup job**'s borg run while offering no SFTP at all, and then the machine is reachable in every way except its files. A machine with no SFTP subsystem has no browsable tree — it has no **SFTP root** either, since there is nothing to be rooted anywhere. |
| **Mounted archive** | An **archive** mounted as a read-only filesystem on its own machine, so the **Explorer** can browse the machine's files as they were when the archive was written — the same directory, the same **paths**, one point in the past. It is time as a third coordinate on an **entry**: the present is the live filesystem, the past is a mounted archive. Read-only by construction — a machine's past cannot be edited, only the present can. |
| **Time rail** | The **Explorer**'s horizontal control for choosing *when* to browse a machine's files: a row of **stops** laid out newest-nearest-Now, plus a **Now** stop for the live filesystem. It appears only on a machine Vaier backs up, and takes its room from the first paint — before the archive list has landed it is drawn empty and dimmed, so the stops fill into a track that is already there rather than shifting the listing down when they arrive. Selecting a stop shows the machine's files as they were in that archive; selecting Now returns to the present. |
| **Stop** | One point in time on the **time rail** — either one of a machine's **archives** (the past) or **Now** (the live present). The stop the operator is standing on decides whether the **Explorer** is showing the past or the present. |
| **Transfer** | A copy of a file or directory from one machine to another across the fleet — the operation the **Clipboard** performs when its **coordinate** is pasted onto a different machine. Because Vaier is the only node with SSH to every machine, a Transfer is a read from the source streamed through Vaier to a write on the destination; no machine ever needs SSH to another. It is a live, ephemeral operation with progress and a settled outcome, not stored history. Its destination is always the present — you can only paste into the present — while its source may be the past, which is what makes a **restore** a Transfer. |
| **Clipboard** | The Explorer's holding area for one file's **coordinate** (its machine, **path**, and point-in-time), carried until it is pasted. Where the coordinate is pasted names the operation: a different machine is a **Transfer**, the browser is a **download**. |
| **Selection** | The set of file **coordinates** the operator has picked in the **Explorer**'s selection bar, to act on together — where the **Clipboard** holds one coordinate, a Selection holds many. It may span machines and points in time, and survives navigation between folders and machines rather than clearing on each move. Its verbs fan out per machine; a Selection of more than one item is **downloaded** as a single zip. |
| **Download** | Sending a file or directory from a machine straight to the operator's browser — the **Clipboard** coordinate pasted to the browser rather than to another machine, or a whole **Selection** streamed as one zip. A read, so it is allowed from the past (an **archive**) as well as the present. A file streams as-is; a directory streams as a zip of its whole tree. |
| **Upload** | Putting a file from the operator's own browser into a directory on a machine — the mirror of a **download**, and the one Explorer operation whose bytes begin outside the fleet. Files only: a folder is not uploaded. Present-only, like every write, because a machine's past is a read-only **mounted archive**. Distinct from a **Transfer**, which carries a **coordinate** between two machines and therefore has a source machine and a point in time; an upload has neither. A name already taken in the destination directory is a **conflict**: the upload is refused rather than replacing what is there, and replacing happens only when the operator asks for it. |
| **Conflict** | The refusal Vaier answers with when a requested name is already in use — an **upload** into a directory that already holds a file of that name. It is a question, not a failure: the operator may confirm the replacement, and only then is the existing file overwritten. A folder wearing the name is a conflict no replacement settles. |
| **Viewable** | Said of a file Vaier will hand to the browser to display rather than only to save. Decided by the file's extension against a fixed allowlist — images, PDFs, common audio and video, and text-ish files, which are all displayed as plain text. A directory is never viewable, and neither is markup a browser can run script from (HTML, SVG and their relatives), because a displayed file is served from Vaier's own origin with the operator's session in reach. |
| **Open** | Displaying a **viewable** file in the operator's browser, in a new tab — the Explorer's second destination for a file's bytes, alongside **download**. A read, so it is allowed from the past (an **archive**) as well as the present. Never replaces **download**: every file can still be saved, viewable or not, and a file that is not viewable can only be saved. |
| **Restore** | Putting an archived file back onto its own live **path** — a **Transfer** whose source is a machine's past (a **mounted archive**) and whose destination is that same machine's present. Not an operation of its own, but the past-to-present case of a Transfer. |
| **Delete** | Removing a file or directory from a machine's live filesystem in the **Explorer**; a directory is removed with everything inside it. Present-only and destructive: there is no point-in-time to delete, because a machine's past (an **archive**) is read-only by construction. It removes what the machine's **effective user** can remove, so the same action reaches further on a machine where that user is **privileged**. A machine's **SFTP root** — its whole browsable tree — is never deletable. |

## 16. Out-of-language

Terms that look like they belong here but don't — these are explicitly **not** Vaier vocabulary because the underlying concept is out of scope:

- Cloudflare, nginx, Caddy, Keycloak, Vault, Kubernetes, Portainer, Coolify, Pi-hole — listed only to record that they were considered and rejected.
- "Backup snapshot" / "export" — Vaier's own configuration export, still out of scope; V2 will add it (see #153). Distinct from **Fleet backup** (§14), which backs up the fleet's machines to a NAS and does exist.
- "Multi-server", "WireGuard mesh" — single Vaier server, period.

## 17. Terms that never appear in the UI

Every term in this document is operator-facing **by default** — it is safe to put in a label, a toast, an error or an email, and doing so is how the product stays consistent with itself. The terms below are the exceptions: they name mechanism the operator did not choose and cannot act on, and the UI says something else instead. They stay in code, comments, this document and the PRD exactly as defined; they are simply never spoken *at* a person.

The one place they may appear on screen is the **Concepts page**, which exists so a curious operator can go deeper. Putting a term here is not a request to rename it — the vocabulary is unchanged; only the copy is.

| Term | What the UI says instead |
|------|--------------------------|
| relay peer | "reached via ‹machine›" — or, said of the machine itself, "machines on its network are reached through it" |
| LAN anchor | never named; the operator sees only which machine a thing is reached via |
| scannable LAN | "the network at ‹site›" — one row per network in the picker, named by the machine it is reached through |
| LAN CIDR, server LAN CIDR | "the network behind it" — normally the network Vaier read off the machine and offered on it ("‹machine› sits on ‹network›"), typed into a machine's form only for a network Vaier cannot see |
| VPN subnet | "your VPN" |
| split tunnel, full tunnel | what the peer *is* — "a server" or "a personal device" — and what that gets it, said plainly |
| AllowedIPs | nothing; it is generated, never shown |
| machine type (`MachineType`) | the one intent question in the add flow; the type itself is never named |
| machine id, peer id | nothing; a machine is identified to a person by its **name** |
| rendered config | "config" — the file handed over once, downloaded or scanned |
| out-of-date config | nothing today: it is computed and served, but no surface reads it. Copy for it would be a new signal, not a rename |
| backup repository | the **store label** — "‹machine›'s backups", or "these backups" where no machine claims the store |
| managed keypair | "Vaier generated this keypair and holds the private half" — the operator meets the **Generate keypair** action and the public key to install, never the adjective |
| fleet-credential standing | never named; the operator sees the **coverage strip** and, per machine, plain words — "In place", "Out of date", "Not delivered", "Write failed", "Unreachable", "No shell access" |
| Claude sign-in state | never named; the operator sees plain words per machine — "Signed in", "Signed out", "Claude isn't installed here", "Unreachable", "No shell Vaier can reach", "Couldn't tell". In a machine's **web terminal**, where the card is already titled Claude, they shorten — "Claude isn't installed here" to "Not installed", "No shell Vaier can reach" to "No shell here". The words are said in Claude's own clay too, faded for signed out, so a machine's terminal and its fleet card agree; the answers that are not a verdict about a sign-in stay quiet, and the read that failed is the one thing here that goes red. On a fleet card the **Claude sign-in standing** says it as a **machine mark** — a chip reading "Claude signed in" or "Claude signed out" in the same clay, hollow when signed out — and only for the first two |
